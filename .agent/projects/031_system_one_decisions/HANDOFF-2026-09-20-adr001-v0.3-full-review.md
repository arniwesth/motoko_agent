## Three questions to answer explicitly, beyond the full pass

**Q-A. The per-row context types (D2 table).** v0.3 gives every slot a context whose `ports` view is
"exactly the `ExtPorts` fields whose rows are subsets of the slot's row": `PureCtx`, `ProcessCtx`,
`FsCtx`, `AiCtx`, `InterceptCtx`, `ProviderCtx`. Re-derive the table from the real rows. Check every
in-tree registration compiles against its new view in principle (named callbacks should, since the
checker infers rows for named functions — confirm). Judge the two row calls v0.3 flags: adding `Trace`
to `ToolProvider`; leaving `{FS}` slots without `clock_now`. Is six types the right cut, or should
it be fewer (e.g. only `PureCtx` + `ExtCtx`) or a different mechanism? Migration cost for the 19
in-tree packages and the two registry-only ones.

**Q-B. The host-mediated transport (D5).** v0.3 says the live `decision_query` arm is a wire exchange
that blocks on the host, row `{IO}`, and the host appends the reservation entry before calling the
provider and the observation before replying, so "recorded before dispatch" is literally true.
Against the actual TUI code: is that implementable as written? Where does `wake_read` block today
and what does the host do on that request? Does putting the decision adapter (HTTP, validation,
basis-point conversion, credentials) in TypeScript create a second implementation of D3's
validation rules that can drift from the child-side codec? Is `{IO}` the right row?

**Q-C. Cross-ADR consistency.** The `Descriptor` resume row (D6/N17) extends ADR-003's refusal set.
The schema-2 strict-superset fold (D7/N20) reverses v0.2's refusal, which the second review had
accepted. "Recorded configuration inputs" (D6/N16) leans on ADR-004 D1. Do these hold against those
ADRs as written, and do they interact with retained counters and reservations (D5) on resume?
