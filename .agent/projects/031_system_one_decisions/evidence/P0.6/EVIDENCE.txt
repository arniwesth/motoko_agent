== What was built (packages/motoko_ext_conformance/examples/) =============
completion_guard.ail       DecisionSolverJudge "example.completion_guard" -- the completion-guard skeleton.
  callbacks  completion_prepare, completion_interpret (named, top-level, bound directly)
  question_config        backend_binding, question_id, max_tool_records=3, candidate_chars=200
  interpretation_config  min_complete_bp=6000, max_feedback_chars=240
  prepare: no decision_state / interventions exhausted / verification Passed -> JudgeImmediate(NoDecision);
           otherwise JudgeQuery(ONE DecisionRequest: one Binary question; state = verification +
           last max_tool_records of tool_evidence + window completeness + candidate excerpt).
  interpret: Unavailable -> NoDecision; Answered below min_complete_bp -> ContinueWithFeedback from its
           own template, BOUNDED by the host's intervention limit (checked again at interpret) and clipped
           to max_feedback_chars; a missing threshold abstains (nothing hard-coded).
repeat_failure_policy.ail  DecisionToolPolicy "example.repeat_failure_policy" -- a no-progress guard.
  callbacks  repeat_prepare, repeat_interpret
  question_config        backend_binding, question_id, window=4, min_failures=2
  interpretation_config  deny_min_bp=7000, max_feedback_chars=200
  prepare: typed failures (CommandExit(n != 0), ToolFailed) of the proposed tool in the last `window`
           records; fewer than min_failures -> ToolImmediate(NoOpinion), else ToolQuery(one request).
  interpret: Unavailable -> NoOpinion; Answered >= deny_min_bp -> Deny(bounded template); else NoOpinion.
config_catalog.ail         DescribeTools consumer (grown from v7_describe_config).
  callback   describe_tools(cfg: Json) -- advertises exactly the names in config.tools
  config     {"tools": [<MOTOKO_EXAMPLE_CATALOG_TOOL>]} or {"tools": []}; the setting is read from the
             environment AT REGISTRATION (as the in-tree extensions read theirs) and reaches the callback
             ONLY through ExtRegistration.config -> the catalog's f(entry.config).
scripted_backend.ail       the scripted backend + host half: register, find the atom in caps, stamp
             ext_config from reg.config, hand back the descriptor projections on decision_state, prepare,
             answer THAT request per question id (usage None: no manufactured zero), interpret with the
             exact prepared request; each vote checked; `catalog_main` for DescribeTools.

Every register_with_config returns ExtRegistration { config, caps } with a literal caps list. The
decision consumers read ONLY the two descriptor projections on decision_state (the D2 conformance
obligation met by construction: nothing reads ext_config for question or vote); the catalog reads only
its (Json) argument, which is ExtEntry.config.
