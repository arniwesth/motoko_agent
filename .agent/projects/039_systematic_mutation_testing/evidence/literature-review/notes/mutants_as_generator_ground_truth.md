## 1. Etna (ICFP 2023; journal version arXiv 2603.27002): exactly what it does

### Takeaway
Etna is a benchmark platform that compares PBT generation strategies by whether, and how fast, they make a fixed property fail on a hand-written mutant; the unit of measurement is a "task", a mutant-property pair known in advance to fail. It holds the properties fixed and does not score their strength, and it records no coverage, so it cannot tell "never reached the mutant" from "reached but not detected".

### Cited Findings
Sources: Shi, Keles, Goldstein, Pierce, Lampropoulos, "Etna: An Evaluation Platform for Property-Based Testing (Experience Report)", PACMPL 7(ICFP) art. 218, 2023, https://doi.org/10.1145/3607860 **[extract]** (author copy https://alperenkeles.com/documents/etna.pdf). Keles, Shi, Kamath, Liu, Mert, Goldstein, Pierce, Lampropoulos, "Etna: An evaluation platform for property-based testing", arXiv 2603.27002v3 **[full]** (sections 1-8; reference list not read). Exa also lists a JFP page at https://jfp.episciences.org/en/articles/17867 **[snippet]**.

- Why mutants and not coverage: "How do we measure the effectiveness of a generator? The software testing literature offers two main answers: code coverage and mutation testing. Code coverage is popular, but problematic: higher coverage does not always translate to better bug finding ... We instead choose mutation testing ... which measures the effectiveness of testing by artificially injecting mutations to the system under test and checking if testing is able to detect them." The section is titled "Evaluate for the ground truth, not for proxy metrics." — [Etna journal version, §2.2.1](https://arxiv.org/html/2603.27002v3)
- Mutants are hand-written, not generated by operators: "Mutations in the literature ... fall on a spectrum from manually sourced to automatically synthesized. We opt for manual sourcing, allowing us to more readily maintain ground truth and ensure that every mutant violates some aspect of the property specification." The same sentence is in the ICFP version. — [Etna journal version, §2.2.1](https://arxiv.org/html/2603.27002v3); [ICFP version](https://alperenkeles.com/documents/etna.pdf)
- Injection mechanism: mutants live in the source file as specially marked comments next to the correct code, and the driver toggles between variants. "They can then encode mutants via special comment syntax embedded within the implementation"; the driver provides "(a) toggling between variant implementations in a directory of workloads; (b) compiling and running each strategy on each task; and (c) analyzing the results." — [Etna journal version, §2.4](https://arxiv.org/html/2603.27002v3)
- Unit of evaluation: "Our mutation-testing based evaluation is built upon tasks: a mutant-property pair where the mutant causes the property to fail." Tasks are grouped into workloads, each with "data type definitions; variant implementations of functions using these types; and a property specification of these functions." — [Etna journal version, §2.3](https://arxiv.org/html/2603.27002v3)
- What is measured: "We run each strategy on each task for a set amount of trials (10 unless otherwise specified) and with a set timeout (60 seconds). We then measure if the strategy was able to solve the task, i.e. find the injected bug in all trials within the given time frame." Results are shown as "task bucket charts" from "solved instantly" to "unsolved"; head-to-head comparisons use Mann-Whitney U tests on time and on valid inputs to failure. — [Etna journal version, §2.5 and §4.1](https://arxiv.org/html/2603.27002v3)
- The oracle is the workload's own property, taken from the literature and fixed across strategies: the BST workload "ports the mutations and properties from" Hughes's How to Specify It!; the IFC workload's violations "are introduced by systematically weakening security checks or taint propagation rules, exploring all possible ways of introducing such violations." Six workloads: BST, red-black trees, STLC, System F with subtyping, a Lua-like parser/printer, IFC. — [Etna journal version, §3.2](https://arxiv.org/html/2603.27002v3)
- Conclusions about generators (journal version): the bespoke generator "solved all tasks, while the naive strategy failed to solve 43 tasks"; "LeanCheck had an 82% solve rate, while SmallCheck's was only 35%"; "Larger trees can be worse for bug-finding, for properties that rely on dependencies between their inputs"; for SmallCheck, reordering property arguments "solved 17 more tasks"; "Specification-derived strategies are on par with bespoke ones"; "Fuzzers exhibit more variance but outperform type-driven methods for sparse preconditions". — [Etna journal version, §4-§5](https://arxiv.org/html/2603.27002v3)
- The mutant benchmark was used to debug a generator, not only to rank it: "by using Etna to evaluate FuzzChick across multiple workloads we were able to identify, isolate, and fix a bug that caused it to saturate the seed pool with uninteresting inputs." — [Etna journal version, §5.2](https://arxiv.org/html/2603.27002v3)
- What it says about the properties themselves: only in passing. The introduction notes "Many aspects of PBT impact its effectiveness, from the properties themselves ... to counterexample minimization ..., but arguably the most crucial one is the algorithm for generating test inputs." The size experiment yields advice on property shape: "the particulars of the mutant and property can lead to dependencies between the property inputs that must be satisfied in order to detect the mutant" and "Testers should prefer properties with fewer inputs where possible." — [Etna journal version, §1 and §4.2](https://arxiv.org/html/2603.27002v3)
- No coverage is recorded: "fuzzing benchmarks generally record code-coverage information, which we plan for Etna to eventually offer as well." — [Etna journal version, §8](https://arxiv.org/html/2603.27002v3)
- Relation to fuzzing benchmarks: the name "was inspired by two existing benchmark suites in the fuzzing space: LAVA ... and Magma"; Etna differs because "PBT is expected to run for less time on programs with higher input complexity." — [Etna journal version, §8](https://arxiv.org/html/2603.27002v3)
- The journal version adds OCaml, Racket and Rust and a cross-language mode that decouples generation from property checking; the ICFP abstract covers "both Coq and Haskell". — [Etna journal version, §1 and §7](https://arxiv.org/html/2603.27002v3); [ICFP version, abstract](https://alperenkeles.com/documents/etna.pdf)
- Later users of the Etna workloads exist: the journal version says Etna "has already been used to assess the positive effects of staging and faster randomness in property-based testing". Exa surfaced Richey, Cutler, Goldstein, Pierce (2026, https://dl.acm.org/doi/10.1145/3798263; a staged-generator paper, probably the staging work meant) and Keles, Miao, Lampropoulos, "Evaluating Shrinking (Experience Report)" (2026, said by its summary to use four Etna workloads) **[snippet for both]**. — [Etna journal version, §1](https://arxiv.org/html/2603.27002v3)

### Inferences
- Etna is the direct precedent for "mutants give a ground truth for the quality of a seeded generator". Its design choice (every task is a pair that is known to fail) removes the property from the experiment: a mutant no property can see is, by construction, not in the benchmark. So Etna measures generators given a sufficient oracle, and says nothing about which invariants are weak. A harness that asks "which of my invariants would have caught this mutant, and which mutants does none of them catch" is asking a question Etna deliberately excludes.
- Etna measures one outcome per run (property failed or not, plus time and input count). Nothing in the text I read measures whether a run reached the mutated code or whether the mutant's run differed from the original's.
- All six workloads are pure data structures, calculi or an abstract machine tested through a pure property. I saw no state-machine (command-sequence) workload in the list; Erlang frameworks are named only as future additions.

### Gaps
- I did not read the ICFP version cover to cover; workload and task counts for that version are not recorded here.
- The repository's per-workload mutant lists (https://github.com/alpaylan/etna-cli) were not read.

## 2. Other property-based testing work that uses mutation (FitSpec, MuCheck, Hughes, QuickChick line, Hypothesis studies, property-set completeness and minimality)

### Takeaway
Using mutants to judge and refine a property set is an established tool-supported practice (MuCheck 2014, FitSpec 2016), and using a fixed bug set to compare both generators and property formulations by mean time to failure was done in 2013 (Hriţcu et al.) and again by Hughes in 2019. FitSpec goes furthest on properties: it reports surviving mutants as evidence of incompleteness and derives minimal property subsets and implications from the kill matrix.

### Cited Findings
- **FitSpec.** Braquehais and Runciman, "FitSpec: Refining Property Sets for Functional Testing", Haskell Symposium 2016, https://doi.org/10.1145/2976002.2976003 (author copy https://matela.com.br/fitspec.pdf) **[extract]**. "FitSpec tests mutant variations of functions under test against a given property set, recording any surviving mutants that pass all tests ... A surviving mutant indicates incompleteness of the property set, prompting the user to amend a property or to add a new one, making the property set stronger. Based on the same test results, FitSpec also provides conjectures in the form of equivalences and implications between property subsets. These conjectures help the user to identify minimal core subsets of properties and so to reduce the cost of future property-based testing." — [FitSpec, abstract](https://matela.com.br/fitspec.pdf)
- FitSpec's two questions are exactly completeness and minimality: "Does the set of properties completely describe the set of functions? ... Is this set of properties minimal? Is there a property that is redundant? When doing regression tests, can a property be excluded to speed up the process?" — [FitSpec, §1](https://matela.com.br/fitspec.pdf)
- Mutants are black-box and enumerated, not source edits: "an enumerative black-box mutation-testing technique that does not need function sources or mutation operators, and always returns a smallest or simplest surviving mutant if there is one". Equivalence of property sets is defined by kills: "Two property sets are apparently equivalent (with respect to specified sets of mutant functions and test arguments) if the property sets kill the same mutants." It works from a kill matrix: "We derive p × m boolean values each indicating whether a mutant survives testing against a property." — [FitSpec, §1 and §4.6](https://matela.com.br/fitspec.pdf)
- Stated limit: "When there are no surviving mutants, we may conjecture that a property-set is complete. However, because of the inevitable limitations of testing, this conjecture could turn out to be false: there may be a mutant beyond those tested that would have survived." Conjectures are less reliable at extreme survival rates: "equivalences and implications are more likely to hold when survival rates for mutants are closer to 50%". — [FitSpec, §3 and §4.6](https://matela.com.br/fitspec.pdf)
- **MuCheck.** Le, Alipour, Gopinath, Groce (author list beyond "Le et al." from memory), "MuCheck: An Extensible Tool for Mutation Testing of Haskell Programs", ISSTA 2014 (tool), https://doi.org/10.1145/2610384.2628052 (copy https://www.uh.edu/serg/publications/issta14tool.pdf) **[extract]**. "MuCheck is a counterpart to the widely used QuickCheck random testing tool for functional programs, and can be used to evaluate the efficacy of QuickCheck property definitions." — [MuCheck](https://www.uh.edu/serg/publications/issta14tool.pdf)
- FitSpec's comparison with MuCheck: "Both MuCheck and FitSpec provide a measure for property-set completeness. Unlike FitSpec, MuCheck: depends on source-code annotations; generates mutants by transformations of the source code; does not provide conjectures or any form of automated guidance towards minimization; may generate mutants equivalent to the original function." — [FitSpec, §6](https://matela.com.br/fitspec.pdf)
- **Hriţcu et al.** Hriţcu, Hughes, Pierce, Spector-Zabusky, Vytiniotis, Azevedo de Amorim, Lampropoulos, "Testing Noninterference, Quickly", ICFP 2013 (https://dl.acm.org/doi/10.1145/2544174.2500574) and JFP 2016, arXiv https://arxiv.org/abs/1409.0393 **[extract]** (text truncated at 110,000 characters; conclusion not read; author list from memory, not shown in the text I read). The abstract ties generators and property formulations to one bug set: "We find that both sophisticated strategies for generating well-distributed random programs and readily falsifiable formulations of noninterference properties are critically important for efficient testing. We propose several approaches and evaluate their effectiveness on a collection of injected bugs of varying subtlety." — [Testing Noninterference, Quickly, abstract](https://ar5iv.labs.arxiv.org/html/1409.0393)
- Measure: "For a given test-generation strategy, we inject the bugs from § 2 one at a time into the machine definition and measure the time spent on average until that bug is found (mean time to failure, or MTTF)." Tables give MTTF per bug per strategy (Naive, Weighted, Sequence, ByExec), with arithmetic and geometric means, tests per second and discard rate. — [Testing Noninterference, Quickly, §4](https://ar5iv.labs.arxiv.org/html/1409.0393)
- The same bug set is then used to compare properties: "In this section we explore a different approach: strengthening the property we are testing so that counterexamples become shorter and easier to find. Figure 18 ... summarizes the variants of noninterference that we consider and how they affect test performance." In Figure 18 the Store*a bug goes from 20018.67 ms MTTF in the first column (EENI, ByExec2 generation) to 16.32 ms in the last (SSNI, "Tiny" generation); the columns differ in property, starting states, equivalence relation and generator together, so the drop is not attributable to the property alone. — [Testing Noninterference, Quickly, §5.4-§6](https://ar5iv.labs.arxiv.org/html/1409.0393)
- **Hughes.** "How to Specify It! A Guide to Writing Properties of Pure Functions", TFP 2019 (LNCS, 2020), https://research.chalmers.se/publication/517894/file/517894_Fulltext.pdf **[extract]**. "To evaluate the properties we have written, we created eight buggy implementations of binary search trees, with bugs ranging from subtle to blatant. The results of testing each property for each buggy version are shown in Figure 8." — [How to Specify It!, §5](https://research.chalmers.se/publication/517894/file/517894_Fulltext.pdf)
- Its conclusions rank property kinds by the bug set: "Validity properties miss many bugs (five of eight), as do 'preservation of equivalence' and 'completeness of insertion' properties. In contrast, every bug is found by at least one postcondition, metamorphic property, and model-based property." "Weak properties miss bugs ... because their preconditions to exclude tricky test cases result in tricky bugs escaping detection." It also measures speed: "we found a counterexample to the property using QuickCheck 1,000 times with different random seeds, and recorded the mean number of tests needed to make that property fail for that bug ... model-based properties find bugs far faster than postconditions or metamorphic properties". — [How to Specify It!, §5.1](https://research.chalmers.se/publication/517894/file/517894_Fulltext.pdf)
- Hughes sets the generator aside explicitly: "We will (largely) ignore the question of how to generate effective test cases". — [How to Specify It!](https://research.chalmers.se/publication/517894/file/517894_Fulltext.pdf)
- **FuzzChick.** Lampropoulos, Hicks, Pierce, "Coverage Guided, Property Based Testing", OOPSLA 2019, https://doi.org/10.1145/3360607 **[abstract]**. "We systematically inject bugs in the machines' checking rules and use FuzzChick to look for counterexamples ... vanilla QuickChick almost always fails to find any bugs after a long period of time ... although highly tuned, hand-written generators can find the bugs faster, they require substantial amounts of insight and manual effort." — [FuzzChick abstract](https://dl.acm.org/doi/10.1145/3360607)
- **Hypothesis in the wild.** Ravi and Coblenz, "An Empirical Evaluation of Property-Based Testing in Python", OOPSLA 2025, https://doi.org/10.1145/3764068 (copy https://cseweb.ucsd.edu/~mcoblenz/assets/pdf/OOPSLA_2025_PBT.pdf) **[extract]**. "we evaluated the efficacy of test suites of 40 projects using mutation testing, and found that on average, each property-based test finds about 50 times as many mutations as the average unit test." It scores property categories by kills: "tests that look for exceptions, that test inclusion in collections, and that check types are over 19 times more effective at finding mutations than other kinds of property-based tests." And it sweeps the input budget: "55% of mutations are found with a single input, and 76% within the first 20." Its warrant for mutants: "Since mutation testing has been found to be a good approximation of real-world bugs [25], we used mutation testing to assess the bug-finding power of each category of test." — [Ravi and Coblenz](https://cseweb.ucsd.edu/~mcoblenz/assets/pdf/OOPSLA_2025_PBT.pdf)
- **Mutants judged against a stated property.** Bartocci, Mariani, Ničković, Yadav, "Property-Based Mutation Testing", arXiv 2301.13615 (2023) **[abstract]**: "(i) a mutant is relevant only if it can impact the satisfaction of the tested properties, and (ii) a mutant is meaningfully-killed with respect to a property only if it causes the violation of that property ... we introduce property-based mutation testing, a method for assessing the capability of a test suite to exercise the software with respect to a given property." Evaluated on Simulink models of cyber-physical systems. — [arXiv 2301.13615](https://arxiv.org/abs/2301.13615)
- **Mutants to assess a harness's properties.** Groce, Ahmed, Jensen, McKenney, Holmes, "How Verified (or Tested) is My Code? Falsification-Driven Verification and Testing", Automated Software Engineering, 2018, https://agroce.github.io/asej18.pdf **[abstract + two sentences]**: "We propose a methodology to allow developers to determine (and correct) what it is that they have verified ... Our basic approach is based on a novel variation of mutation analysis and the idea of verification driven by falsification." Workflow: "At each stage the developer examines the currently surviving mutants, either by inspecting the mutated code or ... looking at successful executions covering the mutant but satisfying the specification given in the harness." — [Groce et al.](https://agroce.github.io/asej18.pdf)
- **Mutants to compare tests with property sets, and to shrink both.** Bradbury, "Using Mutation for the Assessment and Optimization of Tests and Properties", Queen's University Technical Report 2006-518, https://research.cs.queensu.ca/TechReports/Reports/2006-518.pdf **[extract]** (a research proposal; "property-based analysis" here means model checking and static analysis, not QuickCheck-style PBT). "Using a mutation-based approach to testing and property-based analysis will allow for the assessment and comparison of test suites and property sets." "The percentage of non-equivalent mutants detected (killed) by a test suite or property set is the mutant score." "test suites and property sets are reduced when the removal of test cases and property sets will not reduce the evaluation result using the metric." Motivated by "industrial code – especially concurrent code". — [Bradbury 2006](https://research.cs.queensu.ca/TechReports/Reports/2006-518.pdf)
- Off-the-shelf practice exists for Rust and Python: cargo-mutants (https://mutants.rs/) and mutmut are general mutation tools that run whatever test suite exists, including proptest or Hypothesis tests **[snippet]**. I found no proptest- or Hypothesis-specific mutation tool.

### Inferences
- "Mutants give a ground truth for the strength of each invariant" is, for pure functions, what FitSpec and MuCheck already do; FitSpec's per-property kill matrix, minimal subsets and implication conjectures are the property-set analogue of per-invariant attribution. Hughes's Figure 8 (property × bug matrix) is the same idea done by hand.
- Hriţcu et al. is the earliest source I found that uses one fixed injected-bug set to measure both axes of half (a) at once: generator quality (MTTF per generation strategy) and property strength (MTTF per noninterference variant). It predates Etna by ten years and comes from the same research group.
- In all of these the property is a pure predicate on a function's input and output. None of the sources I read applies a kill matrix to invariants judged over an execution trace of a simulated system.

### Gaps
- MuCheck's paper was read only for its framing sentence; its evaluation was not read.
- Duregård's thesis work on black-box mutation testing and the Mutaml tool for OCaml (QCheck) were not searched for separately; neither surfaced.
- Whether any QuickCheck-family tool reports per-property kill attribution for stateful (state-machine) properties: not found.

## 3. Stateful or model-based property testing evaluated with mutants or seeded bugs

### Takeaway
I found no peer-reviewed work that uses a fixed mutant set to compare command or workload generators for state-machine PBT in the QuickCheck family. The nearest matches are two unreviewed 2026 GitHub projects that do exactly the DST version of half (a): plant Raft bugs in a deterministic simulator, count seeds or trials to first catch, attribute each catch to an invariant, and (in one) compare three search strategies.

### Cited Findings
- **asp53826/dst-harness** (GitHub, created 2026-07-31, 0 stars, Python; unreviewed), https://github.com/asp53826/dst-harness **[README, first ~7,000 of 12,183 characters read]**. Repository description: "Deterministic simulation testing: virtual clock, network and disk, seeded fault injection, linearizability checking - measured by how many seeds it takes to catch twelve planted Raft bugs". Rationale: "A test suite that has never found a bug is indistinguishable from a test suite that cannot find one. So the first thing to measure is not whether the code passes. It is how much searching it takes to find a bug you put there yourself." — [dst-harness README](https://github.com/asp53826/dst-harness)
- Its table has columns "mutant | seed | caught by": "Twelve defects, each one a mistake that has been made in a real Raft, planted one at a time. The number that matters is ... how many seeds it took". Seeds to first catch range from 1 to 485 (`figure8`), with a clean-code control of "no violation in 2,000 seeds". — [dst-harness README](https://github.com/asp53826/dst-harness)
- Per-oracle attribution: "`kv_no_dedup` and `local_read` are caught only by the linearizability checker, and never by any Raft invariant ... Checking the protocol's own properties would report a clean bill of health on both." It separates crash from check: "`commit_no_clamp` is caught by an exception, not a check. That is reported as `crash` rather than folded into the invariant column." — [dst-harness README](https://github.com/asp53826/dst-harness)
- A surviving mutant exposed a workload weakness: "`single_slot` survived 400 seeds, and instrumenting the disk showed why - five torn writes in sixty runs. Crashes drawn uniformly over a six-second run essentially never land inside a 4ms fsync window, so a fault that existed in the model was, in practice, unreachable. A fault in the model is not the same as a fault the campaign will reach, and the only way to tell them apart is to plant a bug that needs it." — [dst-harness README](https://github.com/asp53826/dst-harness)
- **Aditya2k5here/counterexample** (GitHub, created 2026-09-05, 0 stars, Python; unreviewed), https://github.com/Aditya2k5here/counterexample **[README, first ~6,000 of 14,000 characters read]**. "a real Raft implementation with eight deliberately seeded defects, six safety invariants, a linearizability checker, and three search strategies competing to find the schedules that break it." Defects are guards in one shared implementation (`if "no_log_up_to_date_check" not in self.bugs:`). — [counterexample README](https://github.com/Aditya2k5here/counterexample)
- It compares generators on the fixed defect set, "Trials until the first violation, budget 300, six independent seeds per cell", with a "caught by" column naming the invariant, and first checks the unmodified implementation for false positives (3,000 schedules, zero). Its conclusion is negative: "Coverage-guided search does not beat random search here, and the bandit does not beat coverage ... At two seeds, the Figure 8 result was bandit 2/2, coverage 1/2, random 0/2 ... Widening to five seeds turned it into 2/5, 1/5, 2/5. The effect was noise". — [counterexample README](https://github.com/Aditya2k5here/counterexample)
- In the peer-reviewed PBT literature, the stateful-flavoured cases with injected bugs are the IFC abstract machines (Hriţcu et al.; FuzzChick; the Etna IFC workload), where programs for a machine are generated and bugs are injected "one at a time into the machine definition". — [Testing Noninterference, Quickly](https://ar5iv.labs.arxiv.org/html/1409.0393)
- Framework documentation for state-machine testing (proptest state machine, PropCheck StateM, Hebert's PropEr book chapter) describes model-versus-SUT checking and shrinking and, per Exa's summaries, does not use mutants **[snippet]**. — [proptest state-machine docs](https://proptest-rs.github.io/proptest/proptest/state-machine.html)
- Concurrency and distributed-systems testing tools are compared on benchmarks of real or collected bugs rather than mutants: Thomson's SCTBench ("49 buggy concurrent software benchmarks drawn from public code bases", per Exa) and Fray (OOPSLA 2025, SCTBench and JaConTeBe plus real-world bugs, per Exa) **[snippet]**. Exa's summaries of ModelFuzz, Mallory, DistFuzz and Tamias say none relies on a fixed set of mutants **[snippet]**. — [Fray](https://dl.acm.org/doi/full/10.1145/3764119)
- Vedder, Arts, Vinter, Jonsson, "Combining Fault-Injection with Property-Based Testing" (2013), https://dl.acm.org/doi/10.1145/2589650.2559629 **[snippet]**: injects environment faults during QuickCheck runs; this is fault injection into the run, not source mutants used as a yardstick.

### Inferences
- The DST form of half (a) is not unknown in practice: both 2026 repositories treat planted bugs as the measure of the harness (seeds to first catch), attribute each catch to a specific invariant or checker, and one uses the planted set to compare workload/schedule search strategies. They are hobby projects with no citations, they use a dozen or fewer hand-planted defects rather than operator-generated mutants, and neither reports reach or state-difference per mutant. They establish that the idea is "in the air" among DST practitioners in 2026, not that it is established literature.
- The dst-harness `single_slot` finding is a concrete instance of the claim "mutants reveal a weak workload generator": the survivor was traced to the fault schedule never hitting a 4 ms window.
- The absence of mutant-based comparisons in the academic distributed-systems testing papers that surfaced (which use real-bug benchmarks) suggests a gap between that literature and the PBT literature, where mutants are standard. This is an inference from a small sample of summaries.

### Gaps
- No full-text check of the distributed-systems fuzzing papers; they are tagged [snippet] and may use seeded bugs in ways the summaries missed.
- Not found: any QuviQ/Erlang QuickCheck state-machine paper that compares command generators on a mutant set; any use of mutants in OCaml multicoretests (Lin/STM). One query each was run; absence of results is weak evidence.
- Industrial DST practice (FoundationDB, TigerBeetle, Antithesis) is assigned to another researcher. The TigerBeetle VOPR doc surfaced but was not read.

## 4. Fuzzer evaluation by mutation analysis and bug-injection benchmarks

### Takeaway
Mutation analysis has been proposed (Gopinath, Görz, Groce 2022) and carried out at scale (Görz et al., USENIX Security 2023) as the ground truth for comparing fuzzers. These works separate "covered" from "killed" and show that both reach and the oracle limit kills: the best fuzzer covers 30.9% of mutants and detects 28.3% of those. Magma and FixReverter instrument each injected bug to report reached, triggered and detected separately.

### Cited Findings
- **Position paper.** Gopinath, Görz, Groce, "Mutation Analysis: Answering the Fuzzing Challenge", arXiv 2201.11303 (2022) **[extract]**. "While mutation analysis is the premier technique for evaluating the quality of software test oracles, mutation score is rarely used as a metric for evaluating fuzzer quality." Against seeded-bug benchmarks: "the basic problem is that the distribution of such bugs is subject to human bias"; "fuzzers can become overfitted to finding bugs in such benchmarks". Against coverage: "structural coverage (which almost always provides no insight into oracles and vulnerability types)". — [arXiv 2201.11303](https://arxiv.org/html/2201.11303v2)
- Its taxonomy already splits reach from detection: "Trivial mutants: These are mutants that can be killed (detected as failure inducing) without targeted intelligence. Stubborn Mutants: These are mutants that remained alive even after coverage reached their mutation locations. Immortal mutants: Mutants that can't be killed by any weak oracles such as crash oracles in the current program." It names oracle quality as a separate axis ("Efficacy of the oracle: The capability of the fuzzer oracle to detect triggered changes in behavior") and notes "Property based testers such as QuickCheck [44] can make use of sufficiently detailed contracts for strong oracles." — [arXiv 2201.11303](https://arxiv.org/html/2201.11303v2)
- **The study.** Görz, Mathis, Haßler, Güler, Holz, Zeller, Gopinath, "Systematic Assessment of Fuzzers using Mutation Analysis", USENIX Security 2023, https://www.usenix.org/conference/usenixsecurity23/presentation/gorz (arXiv 2212.03075) **[extract]**. Framing: "In software testing, the gold standard for evaluating test quality is mutation analysis, which evaluates a test's ability to detect synthetic bugs: If a set of tests fails to detect such mutations, it is expected to also fail to detect real bugs." — [arXiv 2212.03075](https://arxiv.org/html/2212.03075v3)
- Covered versus detected, with numbers: "The best fuzzer in our evaluation, AFL++, covers 30.9% of all mutations and detects 28.3% of these covered mutants—that is, 8.8% of all mutations." Sanitizers help little: "using an enhanced oracle such as Address Sanitizer [28] results in a moderate improvement in detection to 34.2% of covered mutants (9.1% of total mutants)." — [arXiv 2212.03075](https://arxiv.org/html/2212.03075v3)
- The kill criterion is weak by design: "A mutation is killed if the original exits with a different exit code than the mutant does." Coverage is checked separately: "During fuzzing, we check if a mutation is covered using the mutated executables." The conclusion on oracles: "fuzzers that use generic oracles, such as crashes or hangs, are quite limited because not every vulnerability (and not every mutation) manifests itself this way"; "out of the mutants that were not detected, few could have been found by a crash oracle". — [arXiv 2212.03075](https://arxiv.org/html/2212.03075v3)
- Mutants hardly steer the fuzzer: "Out of all mutants killed by AFL++ (28.3% of covered mutants), 94.4% were found with inputs generated on an unmutated binary." A corpus is reused as a fixed suite: "This seed corpus is then used as a static test suite to kill trivial mutants, leaving the few remaining ('stubborn') ones as potential fuzzing targets." — [arXiv 2212.03075](https://arxiv.org/html/2212.03075v3)
- Mutants versus real bugs: "we find that 71 of 100 recent CVEs were coupled to a mutation", where "A mutation is identified as coupled to a vulnerability if this mutation reintroduces the vulnerability into the patched program." Equivalent mutants: "We manually analyzed a random sample of 100 stubborn mutants and found only 11 equivalent mutants." Agreement with other methods: "Our experiments largely confirm the fuzzer ranking established in previous literature". Cost: "evaluating a single fuzzer takes 4.09 CPU years"; supermutants cut runs by a mean of 3.8×. — [arXiv 2212.03075](https://arxiv.org/html/2212.03075v3)
- It names comparing the mutant's behaviour with the original's as future work: "We can compare the behavior (even coverage) of a mutant against the original using differential fuzzing and identify whether a fuzzer was able to induce a change in behavior compared to the original even in the absence of a suitable sanitizer." — [arXiv 2212.03075, §7](https://arxiv.org/html/2212.03075v3)
- **Magma.** Hazimeh, Herrera, Payer, "Magma: A Ground-Truth Fuzzing Benchmark", Proc. ACM Meas. Anal. Comput. Syst. 4(3), 2020, https://doi.org/10.1145/3428334 (arXiv 2009.01120) **[extract]**. Real bugs forward-ported by hand, each with a canary: "each reinserted bug is accompanied by a light-weight oracle that detects and reports if the bug is reached or triggered." "A bug is reached when the faulty line of code is executed, and triggered when the fault condition is satisfied." "This distinction between reaching and triggering a bug—in addition to a fuzzer's ability to detect a triggered bug—presents a new opportunity to evaluate a fuzzer across multiple dimensions". It warns that the instrumentation can leak: "if oracles were implemented as if statements, fuzzers that maximize branch coverage could detect the oracle's branch". On LAVA: "the LAVA bug injection technique only injects a single, simple bug type: an out-of-bounds memory access triggered by a 'magic value' comparison." — [arXiv 2009.01120](https://arxiv.org/html/2009.01120)
- **FixReverter.** Zhang, Patterson, Hicks, Wei, "FixReverter: A Realistic Bug Injection Methodology for Benchmarking Fuzz Testing", USENIX Security 2022, https://www.usenix.org/conference/usenixsecurity22/presentation/zhang-zenong **[extract]**. Three states per injected bug: "Not reached: the fuzzer never reaches the conditional statement; Reached: some inputs generated by the fuzzer reach the conditional statement; Triggered: the reversed condition(s) with tracer is satisfied ... Similar bug states are used in Magma". Result: "1927 (24%) and 638 (8%) of all 7910 injected bugs were reached and triggered, respectively"; "Over 40% (91 out of 219) individual bugs were detected by all fuzzers". Critique of earlier injectors: "Both LAVA and Apocalypse arguably fail G2, since the injected patterns do not resemble realistic bugs." Automated injection is argued to defend against overfitting because "the tool can be used to produce new, fault-injected programs as often as needed". — [FixReverter paper](https://www.usenix.org/system/files/sec22-zhang-zenong.pdf)
- **Synthetic versus organic bugs.** Bundt, Fasano, Dolan-Gavitt, Robertson, Leek, "Evaluating Synthetic Bugs", arXiv 2208.11088 **[abstract]**: eight fuzzers, 20 targets, "over 80 years of CPU time"; "no fuzzer found any organic bugs (i.e., one reported in a CVE), despite 50 such bugs being available"; "a dramatic difference between where synthetic and organic bugs live with respect to the 'main path' discovered by fuzzers"; synthetic bugs "are still significantly easier to find than organic bugs in our target programs." — [arXiv 2208.11088](https://arxiv.org/abs/2208.11088)
- **Mutants as stand-ins in testing experiments generally.** Andrews, Briand, Labiche, "Is Mutation an Appropriate Tool for Testing Experiments?", ICSE 2005, https://doi.org/10.1145/1062455.1062530 **[abstract]**: "the use of mutation operators is yielding trustworthy results (generated mutants are similar to real faults). Mutants appear however to be different from hand-seeded faults that seem to be harder to detect than real faults." — [Andrews et al.](https://dl.acm.org/doi/10.1145/1062455.1062530)
- Just, Jalali, Inozemtseva, Ernst, Holmes, Fraser (co-authors after Just from memory), "Are Mutants a Valid Substitute for Real Faults in Software Testing?", FSE 2014, https://doi.org/10.1145/2635868.2635929 **[extract]**: "The results show a statistically significant correlation between mutant detection and real fault detection, independently of code coverage"; "a coupling effect for 73% of real faults"; "17% of real faults are not coupled to mutants". The paper notes "mutation analysis is commonly used to evaluate and compare (generated) test suites". — [Just et al.](https://homes.cs.washington.edu/~rjust/publ/mutants_real_faults_fse_2014.pdf)
- Namin and Kakarla, "The Use of Mutation in Testing Experiments and its Sensitivity to External Threats", ISSTA 2011, https://doi.org/10.1145/2001420.2001461 **[abstract; author names from memory, not shown in the fetched text]**: "mutation when used in testing experiments is highly sensitive to external threats caused by some influential factors including mutation operators, test suite size, and programming languages." — [ISSTA 2011](https://dl.acm.org/doi/10.1145/2001420.2001461)

### Inferences
- The fuzzing literature already holds the two-level split the claim's half (b) relies on (covered versus killed in Görz et al.; reached, triggered, detected in Magma and FixReverter). What it lacks, in the sources read, is the middle measurement taken by comparing the mutant's run to the original's on the same input; Görz et al. list it as future work, and Mu2 (question 5) uses output difference as its kill criterion.
- The evidence on realism points both ways and depends on how bugs are made. Operator-generated mutants: 71 of 100 CVEs coupled (Görz), 73% of real faults coupled (Just), "trustworthy" (Andrews). Pattern-injected bugs (LAVA): easier than organic bugs and living on the main path (Bundt). Hand-seeded faults: harder than real ones in Andrews et al. Etna and both 2026 DST repositories use hand-planted bugs, the category with the least validation.
- Görz et al.'s numbers say that for crash-only oracles, most covered mutants go undetected (about 72% for the best fuzzer). A harness with trace invariants is on the "strong oracle" side of the divide that paper asks for, which is where per-invariant kill attribution becomes meaningful.
- Overfitting to a fixed bug set is a recognised risk (Gopinath et al.; FixReverter's goal G4; Magma's leaky-oracle section). It applies equally to a fixed mutant corpus used to tune a workload generator.

## 5. Model-based mutation testing, mutation-driven generation, and mutant kill sets for selecting, reducing or prioritising a suite or corpus

### Takeaway
Using mutants to drive what gets generated and what gets kept is established: model-based mutation testing generates tests that kill model mutants (Aichernig et al., MoMuT), Mu2 keeps a fuzzer input only if it kills a new mutant, and test-suite reduction that preserves the kill set is a known technique. I read only abstracts or summaries for most of this, so it is recorded as existence, not detail.

### Cited Findings
- **Mu2.** Vikram, Laybourn, Li, Nair, OBrien, Sanna, Padhye, "Guiding Greybox Fuzzing with Mutation Testing", ISSTA 2023, https://doi.org/10.1145/3597926.3598107 (copy https://rohan.padhye.org/files/mu2-issta23.pdf) **[extract]**. "after a new input is synthesized by a fuzzer via random mutation of a previously saved input, it is evaluated by executing a set of mutants of the program under test"; "Inputs are saved to the corpus if they improve mutation score." "Mu2 makes use of a differential oracle for identifying inputs that exercise interesting program behavior without causing crashes." Motivation: "in the vast majority of fuzzing research, the end goal is to find bugs in the moment [42]; not much attention is paid to the inputs saved along the way." Result: "variants of Mu2 are able to synthesize test-input corpora with a higher mutation score than state-of-the-art Java fuzzer Zest", "with up to 20% increase in the Jackson JSON parser". Its RQ4 asks "How much stronger is the differential mutation testing oracle than the implicit oracle?" — [Mu2](https://rohan.padhye.org/files/mu2-issta23.pdf)
- **Model-based mutation testing.** "Killing strategies for model-based mutation testing", Software Testing, Verification and Reliability, 2015, https://doi.org/10.1002/stvr.1522 **[abstract; authors as I recall them: Aichernig, Brandl, Jöbstl, Krenn, Schlick, Tiran, not shown in the fetched text]**: "Mutation operators are employed on the level of the specification to insert faults and generate test cases that will reveal the faults inserted." It reports "an in-depth evaluation of different fault-based test case generation strategies on each of the case studies ... and a comparison with plain random testing", and discusses "how to gain a more expressive test suite by combining cheap but undirected random test case generation with the more expensive but directed mutation-based technique." — [STVR abstract](https://onlinelibrary.wiley.com/doi/10.1002/stvr.1522)
- Related items seen only as Exa summaries **[snippet]**: Krenn, Schlick, Tiran, Aichernig, Jöbstl, Brandl, "MoMuT::UML Model-Based Mutation Testing for UML" (ICST 2015); Aichernig, Brandl, Jöbstl, Krenn, "Efficient Mutation Killers in Action" (ICST 2011); Aichernig, Marcovic, Schumi, "Property-Based Testing with External Test-Case Generators" (2017), which per its summary feeds model-based mutation tests into a PBT tool; Fellner et al., "Model-based, Mutation-driven Test-case Generation Via Heuristic-guided Branching Search" (https://dl.acm.org/doi/fullHtml/10.1145/3289256).
- **Kill sets for reduction and prioritisation** **[snippet for all]**: Shi, Gyori, Gligoric, Zaytsev, Marinov, "Balancing Trade-Offs in Test-Suite Reduction" (FSE 2014, https://dl.acm.org/doi/pdf/10.1145/2635868.2635921), which per Exa's summary includes reduction that keeps the set of killed mutants; Gonzalez-Hernandez, Lindström, Offutt, Andler, Potena, Bohlin, "Using Mutant Stubbornness to Create Minimal and Prioritized Test Sets" (2018); Zhang, Marinov, Khurshid, "Faster Mutation Testing Inspired by Test Prioritization and Reduction" (ISSTA 2013). Vikram, Padhye, Sen, "Growing a Test Corpus with Bonsai Fuzzing" (ICSE 2021) per its summary evaluates a fuzzing corpus by mutation score.
- FitSpec applies the same idea to properties rather than tests: minimal property subsets "to reduce the cost of future property-based testing". — [FitSpec](https://matela.com.br/fitspec.pdf)
- Bradbury's 2006 proposal states the reduction rule for both: "test suites and property sets are reduced when the removal of test cases and property sets will not reduce the evaluation result using the metric." — [Bradbury 2006](https://research.cs.queensu.ca/TechReports/Reports/2006-518.pdf)

### Inferences
- "Mutants give the value of each corpus member" is Mu2's corpus-admission rule stated for a fuzzer: an input earns its place by killing a mutant no saved input kills. Mu2's kill criterion is a difference in output between mutant and original, which is close to the "run differed from the unmutated run" measurement in half (b), used as the admission signal.
- Model-based mutation testing mutates the model and generates the distinguishing test; the claim under review mutates the implementation and scores an existing generator. These are different directions of the same relation, and the STVR abstract's conclusion (combine random with mutation-directed generation) is about generation cost, not about judging invariants.
- Together with questions 1-4: each ingredient of half (a) has a named precedent (generator quality: Hriţcu 2013, Etna 2023, Görz 2023; property strength: MuCheck 2014, FitSpec 2016, Hughes 2019; corpus value: Mu2 2023, kill-preserving reduction). What I did not find in reviewed literature is their combination inside a deterministic simulation harness with trace-level invariants; the 2026 repositories in question 3 do a hand-planted version of it.

### Gaps
- None of the model-based mutation testing papers was read beyond one abstract; results on how model-mutant-derived suites perform against implementation faults are not recorded.
- The test-suite reduction and prioritisation items are [snippet] only; the size of fault-detection loss under kill-preserving reduction is not recorded.
- No source found that uses mutant kill sets to minimise a seed corpus for a deterministic simulator.
