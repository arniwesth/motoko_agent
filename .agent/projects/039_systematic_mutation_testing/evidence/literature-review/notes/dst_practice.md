# DST practice: how simulators, oracles and workloads are validated, and whether DST has been combined with mutation testing

Researcher notes, 2026-10-06. Search backend: Exa only (29 searches, 10 full-text fetches). Raw responses: `/workspaces/motoko_agent/tmp/research/exa_raw/dst_practice/` (`sNN_*.json` = searches, `cNN_*.json` = full-text fetches).

Reading-depth tags used on every source: **[full]** = full text fetched and the relevant sections read; **[grep]** = full text fetched, keyword-searched, matching passages read; **[summary]** = only Exa's query-focused summary read (quotes are as relayed by that summary and were not checked against the page); **[title]** = title/metadata only.

Headline for the report writer: **the claim is not new in its core.** Antithesis published a DST + mutation-testing workflow on 2026-09-25 (skill dated 2026-09-23) that already sorts each mutant into "caught / buggy code never ran / bug ran, nothing noticed / no usable result" and diagnoses survivors as bad workload, bad oracle, bad mutant or bad property. A September 2026 arXiv paper (Chronicle) does source mutation under deterministic replay of LLM agents and sorts survivors into unreached-or-equivalent vs. ignored-by-assertion. What I did not find is listed under Inferences in Q2.

## Q1. Do the well-known DST projects describe source mutation, bug seeding, re-introducing fixed bugs, or sensitivity checks?

### Takeaway
Antithesis does, explicitly and in three forms (customer bug seeding documented as "brown M&Ms", re-introduction of fixed production bugs, and since September 2026 an agent skill for mutation testing). One small project (konserve) reports hand mutation of its simulation suite. FoundationDB, TigerBeetle, AWS ShardStore, Dropbox, Jepsen/Maelstrom, Resonate, RisingWave/MadSim, Turmoil, Shuttle, Polar Signals, WarpStream, sled and S2 say nothing about mutation or bug seeding in the material I retrieved; they use coverage/reachability and escaped-bug post-mortems instead.

### Cited Findings

**Antithesis (positive, three forms)**
- Docs page "Is Antithesis working?" [full] defines the practice: "A brown M&M is a bug that you know is present in your software, and that you know your workload and test setup should be able to find. Run your tests with the brown M&Ms present — if Antithesis finds the bug, then you can have confidence that your tests are really working." — [Antithesis Docs, "Is Antithesis working?", n.d.](https://antithesis.com/docs/best_practices/is_antithesis_working/)
- Same page, section "Deliberately introduce a bug": "Some of our most engaged customers have a sneaky practice of slipping a deliberate bug into one of their Antithesis builds, as a test of whether we can catch it. Sometimes this is an artificial bug designed to be hard to find, and sometimes this is re-introducing a true production bug that was previously solved." — [same](https://antithesis.com/docs/best_practices/is_antithesis_working/)
- Same page treats escaped production bugs as test-setup defects: "Our philosophy is that any bug that reaches production for our customers is a bug in Antithesis. This could be due to a weakness in your test setup (perhaps the test template you wrote doesn't even call the function that triggers the bug), or it could be a weakness in Antithesis". — [same](https://antithesis.com/docs/best_practices/is_antithesis_working/)
- Mutation-testing skill and blog post: see Q2 and Q4.

**FoundationDB (negative on mutation; positive on reachability)**

For example, a developer concerned that a new piece of code may rarely be invoked with a full buffer can add the line TEST( buffer.is_full() ); and analysis of simulation results will tell them how many distinct simulation runs achieved that condition. If the number is too low, or zero, they can add buggification, workload, or fault injection functionality to ensure that scenario is adequately tested." — [Zhou et al., "FoundationDB: A Distributed Unbundled Transactional Key Value Store", SIGMOD 2021](https://www.foundationdb.org/files/fdb-paper.pdf)

**TigerBeetle / VOPR (negative on mutation; positive on escaped-bug analysis)**
- "Fuzzer Blind Spots (Meet Jepsen!)" [grep; most of the post read] analyses a query bug Jepsen found that ~20 fuzzers missed, and states the same two-way split the claim calls world gap vs. oracle gap: "the VOPR and LSM query fuzzer both missed the bug, with two possibilities: The fuzzer workloads never generate an input which triggers the bug. ### Inferences
- Before September 2026 the documented industry practice was ad hoc bug seeding (Antithesis customers) plus reachability instrumentation; systematic or per-property mutation of a DST target appears first in Antithesis's skill.
- The world-gap / oracle-gap distinction is established vocabulary in practice (TigerBeetle 2025, ShardStore 2021, Antithesis docs), though under other names and derived from escaped bugs, not from mutants.

### Gaps
- Loom: no Loom page was returned; nothing checked. Will Wilson's Strange Loop 2014 talk and BugBash talks: not retrieved (video, no transcript in results).
- All "summary-only" negatives could hide a sentence the summariser dropped; only FDB, ShardStore, Dropbox, TigerBeetle (one post) and Antithesis were checked against page text.
- TigerBeetle: I did not verify whether the repo has an intentionally failing "canary" fuzzer or coverage "marks"; the summary of `fuzz_tests.zig` mentions "a canary/smoke setup" without detail.

## Q2. Is there a publication that names DST and mutation testing together, and what does it do?

### Takeaway
Yes: Antithesis, "Why we taught agents to break distributed safety properties" (Rohan Padhye, 2026-09-25), with the open `antithesis-mutation-testing` skill. It injects LLM-designed source mutants into a DST target, uses a reachability marker plus the property verdict to classify each attempt, and feeds survivors back into workload, oracle or property fixes. I found no peer-reviewed paper that uses the term "deterministic simulation testing" together with mutation testing.

### Cited Findings
- Purpose [full]: "we've just developed a new agent skill to perform mutation testing, injecting artificial bugs to validate or refine Antithesis tests until properties are falsifiable (i.e., the test should fail when a property-violating bug is present)." — [Padhye, Antithesis blog, 2026-09-25](https://antithesis.com/blog/2026/mutation-testing/)
- Per-attempt outcome classes shown in the post's results table: "Artificial bug was caught", "Buggy code never ran", "Bug ran, nothing noticed", "No usable result". — [same](https://antithesis.com/blog/2026/mutation-testing/)
- Scale and result on rqlite: "After 19 mutant injections across 46 runs of 15-60 minutes each (~24 hours cumulative fuzzing duration), the agent ended the mutation testing campaign reporting that 11 of 13 safety properties were successfully falsified". The two misses are attributed to test setup (disk faults not enabled) or the property itself. — [same](https://antithesis.com/blog/2026/mutation-testing/)
- Survivors drive repairs: "If the test results indicated that the property was not falsified (i.e. the test passed despite the bug we injected), then the agent autonomously iterated further by refining one or more of the mutant, workload, assertion, or test configuration." Table entries include "Added a check inside rqlite", "New driver: hold the WAL open", "Added node stops to the fault mix", "Doubled the run length". — [same](https://antithesis.com/blog/2026/mutation-testing/)
- It rejects operator-based syntactic mutation for this setting: "For end-to-end testing of distributed systems, however, simple syntactic changes are not good mutations because they mostly lead to run-time panics and short-circuit the validation of distributed safety properties such as consensus or durability." — [same](https://antithesis.com/blog/2026/mutation-testing/)
- Generality claim: "Mutation testing is a powerful but under-appreciated technique, and we believe the takeaways from this post apply even beyond Antithesis." — [same](https://antithesis.com/blog/2026/mutation-testing/)
- Skill definitions [SKILL.md: about 22k of 25.5k chars read]: "Validate the *oracle*, not the system under test. A green run shows nothing bad was observed — not that the property would have noticed." "**Marker:** A signal carried by a mutant patch at the point of divergence, proving the buggy code executed." "**Baseline:** A run of the unpatched SUT built from the same source as every mutant. The control." "**Survived:** The mutant ran, the buggy code executed, and the targeted property still passed. Usually a defect in the mutant, oracle, workload, or property". — [antithesishq/antithesis-skills, antithesis-mutation-testing/SKILL.md, version "2026-09-23 a8fe900"](https://github.com/antithesishq/antithesis-skills/blob/main/antithesis-mutation-testing/SKILL.md)
- Verdict ladder [references/sweep-and-verdicts.md: "Gates" and "The verdict ladder" sections read]. Rows include: "Marker red, and nothing reaches the **mutated site** … | **bad workload**"; "Marker red, but the mutated site **is** reached … only the divergence condition failed to occur | rarity, not a gap"; "Marker green, divergence masked or converged before observation | **bad mutant** | The bug ran but was erased before anything could see it"; "Marker green, divergence reaches the assertion but the predicate tolerates it | **bad oracle** | The catalog has a hole and the mutant found it"; "No observation point could ever distinguish a violation | **bad property**". — [sweep-and-verdicts.md](https://github.com/antithesishq/antithesis-skills/blob/main/antithesis-mutation-testing/references/sweep-and-verdicts.md)
- Reach vs. divergence is distinguished [references/mutant-design.md: marker section read]: "Place the marker where the mutation actually diverges, not where the enclosing function is entered … Where a conditional placement is not cheap to express, site entry is acceptable — record in the mutant's evidence file that the marker proves reach but not divergence". — [mutant-design.md](https://github.com/antithesishq/antithesis-skills/blob/main/antithesis-mutation-testing/references/mutant-design.md)
- Runs are samples, not paired seeds: "One 15-minute randomized run is a sample, though, and it under-samples exactly the deep, rare states most worth validating" (SKILL.md); attribution is by co-occurrence inside one history: "Marker green, target red, but no counterexample history carries the marker | **unattributed** | Both counts are run-wide totals, so these may be different histories." — [SKILL.md](https://github.com/antithesishq/antithesis-skills/blob/main/antithesis-mutation-testing/SKILL.md); [sweep-and-verdicts.md](https://github.com/antithesishq/antithesis-skills/blob/main/antithesis-mutation-testing/references/sweep-and-verdicts.md)
- Design limits stated by the skill: "**One mutant per property, modeling a realistic mistake.** A dropped guard, a flipped comparator, an off-by-one, a missing clamp — not vandalism." `Sometimes` and `Reachable` assertions are "Baseline only" (not mutated). — [SKILL.md](https://github.com/antithesishq/antithesis-skills/blob/main/antithesis-mutation-testing/SKILL.md)
- Academic search for the exact term with mutation (`s02`, `s14`, `s22`, `s28`) returned distributed-systems testing papers evaluated by new bugs and coverage, e.g. Tamias "found 12 new bugs and showed up to 22% improvement in branch coverage" [summary] — [Tamias, SOSP 2026](https://dl.acm.org/doi/10.1145/3830418.3843891); Mocket "reports 3 previously unknown bugs" [summary] — [Wang et al., EuroSys 2023](https://dl.acm.org/doi/10.1145/3552326.3587442). None combines DST with mutation analysis.

### Inferences
- Part (a) of the claim (mutants as ground truth for invariant strength) is prior art as of 2026-09-25: the Antithesis skill does exactly this per property. Part (b)'s sorting of survivors is also substantially prior art: "buggy code never ran" / "bug ran, nothing noticed" / "caught", refined into bad workload, rarity, bad mutant (masked), bad oracle, bad property.
- Differences I can support from the text read, which may be what remains of the claim: (1) Antithesis compares a mutant campaign with a separate randomized baseline run and attributes by marker co-occurrence; it does not run mutant and original on the same seed and diff the traces, so it has no direct "run differed from the unmutated run" measurement; "divergence masked or converged before observation" is a diagnosis the agent reaches from its kill-chain trace and the run's logs, as far as the sections I read show. (2) It uses one hand-designed (LLM-designed) semantic mutant per property, explicitly not operator-generated source mutants, and reports no mutation score over a mutant population. (3) It gives verdicts per property; I saw nothing that scores individual corpus members/seeds or a seeded workload generator, though "bad workload" is a diagnosis. (4) The target is a distributed database, not an LLM agent loop.
- The Antithesis argument that syntactic mutants "mostly lead to run-time panics" is a direct objection to operator-based mutation in end-to-end DST; a claim built on source-level operators should answer it with data.

### Gaps
- Not read in the skill: `references/evidence-and-report.md`, `static-validation.md`, `mutation-harness.md`, `resume.md`, `catalog-reconstruction.md`, and the tail of SKILL.md. A same-seed or trace-diff step could be described there; inference (1) is limited to the parts read.
- The blog's interactive per-attempt details did not render in the fetched text.
- No BugBash/HYTRADBOI/P99 talk on this was found; conference video content is poorly covered by Exa.

## Q3. How do these projects measure the quality of a DST setup at all?

### Takeaway
Mostly by reachability of declared rare conditions across runs (FDB `TEST`/code probes, Antithesis sometimes-assertions), code coverage, bugs found and time-to-find, and post-mortems of bugs that escaped to production, Jepsen or code review. Seeded or re-found known bugs appear as a measure only in Antithesis's docs.

### Cited Findings
- Reachability counts over the run ensemble: FDB `TEST( buffer.is_full() )` quote in Q1. — [Zhou et al., SIGMOD 2021](https://www.foundationdb.org/files/fdb-paper.pdf)
- Latency to discovery as a metric: "Finding bugs quickly is important both so that they are encountered in testing before production, and for engineering productivity". — [Zhou et al., SIGMOD 2021](https://www.foundationdb.org/files/fdb-paper.pdf)
- Antithesis on detection frequency of a known bug: "latency to finding a bug is … an indication of testing strength: if the common bugs are found immediately, then the rare bugs may be found eventually" and "Once an issue has been discovered by Antithesis, do we then discover it with every subsequent test until it's fixed? If not, you should be dissatisfied". — [Antithesis Docs](https://antithesis.com/docs/best_practices/is_antithesis_working/)
- Sometimes-assertions as a substitute for seeding: "Instead of re-introducing the bug, add a sometimes assertion in the transaction rollback code which asserts that more than a certain fraction of memory is in use … This can give you great peace of mind that we would find that bug right away if it were ever accidentally reintroduced". — [Antithesis Docs](https://antithesis.com/docs/best_practices/is_antithesis_working/)
- "Sometimes assertions are a better version of traditional code coverage metrics and give critical insight into whether your Antithesis testing is effective." [summary] — [Antithesis Docs, "Sometimes Assertions"](https://antithesis.com/docs/best_practices/sometimes_assertions/)
- Will Wilson, quoted by Phil Eaton [grep; passage read]: "it's terrifyingly easy to build a DST system that appears to be doing a ton of testing, but actually never explores very much of the state space of your system. At FoundationDB, the vast majority of the work we put into the simulator was an iterative process of hunting for what wasn't being covered by our tests and then figuring out how to make the tests better." — [Eaton, "What's the big deal about Deterministic Simulation Testing?", 2024-08-20](https://notes.eatonphil.com/2024-08-20-deterministic-simulation-testing.html)
- ShardStore: code coverage for blind spots; outcome metric "prevented 16 production issues" [summary of abstract]; one escaped bug analysed (Q1). — [Bornholt et al., SOSP 2021](https://dl.acm.org/doi/10.1145/3477132.3483540)
- TigerBeetle: external black-box test (Jepsen) as a check on the fuzzers, followed by a root-cause of the blind spot (Q1). — [TigerBeetle blog 2025](https://tigerbeetle.com/blog/2025-06-06-fuzzer-blind-spots-meet-jepsen/)
- Turso: paid bounty for bugs the simulators miss (Q1). — [Turso blog 2026](https://turso.tech/blog/the-wonders-of-ai)
- Resonate: saturation of an abstract state signature, not code coverage: "the run ends only after all twenty-two operation kinds are covered and twenty consecutive 200-step batches produce no new (operation, status, state-shape) combination — a stopping heuristic over the protocol surface, not a code-coverage measure" [summary]. — [Resonate docs](https://docs.resonatehq.io/evaluate/how-resonate-is-tested)
- WarpStream reports time-to-find for a real bug ("[caug]ht by Antithesis in 233 seconds that went undetected in thousands of hours of prior testing") [summary, truncated quote]. — [WarpStream blog](https://www.warpstream.com/blog/deterministic-simulation-testing-for-our-entire-saas)
- konserve notes assertion count is misleading: "Assertion count is a poor proxy for sensitivity here". — [konserve doc](https://github.com/replikativ/konserve/blob/main/doc/simulation-testing.md)

### Inferences
- Reachability probes answer only the first of the claim's three measurements ("did the run reach it"); escaped-bug post-mortems answer the other two after the fact and one bug at a time. This is the gap the Antithesis skill and the claim both aim at.

### Gaps
- No project publishes a quantitative mutation score, or time-to-detect distribution for seeded bugs, for its DST harness.
- Academic model-guided fuzzing work appears to use a seeded bug as one evaluation subject (Gulcan, Kulahcioglu Ozkan, Majumdar, Nagendra, "Model-guided Fuzzing of Distributed Systems", 2024); I have only Exa's library copy (https://exa.ai/library/publication/jmr5sv6gvz3) and a paraphrased summary, canonical URL not resolved.

## Q4. What do Antithesis's docs and the antithesis-skills repository say about mutation testing or assertion sensitivity?

### Takeaway
The docs recommend bug seeding and re-introduction under the name "brown M&Ms" and offer sometimes-assertions as the non-invasive alternative. The skills repo has a dedicated `antithesis-mutation-testing` skill (version string 2026-09-23) whose stated goal is to validate the oracle, with a baseline gate, a three-part mutant patch (announcement, marker, change), a verdict ladder and rules against gaming.

### Cited Findings
- Docs: quotes in Q1 and Q3. — [Antithesis Docs, "Is Antithesis working?"](https://antithesis.com/docs/best_practices/is_antithesis_working/)
- Repo README lists the skill [grep]: "`antithesis-mutation-testing` validates that your property catalog can actually catch bugs. A property that passes every run tells you nothing bad was observed" and "Once a baseline run comes back green, `antithesis-mutation-testing` checks that your properties can actually fail — a green run proves nothing was observed, not that anything would have been noticed." — [antithesishq/antithesis-skills](https://github.com/antithesishq/antithesis-skills)
- Skill description: "For each safety property, inject one realistic mutant into the SUT, run it, and confirm the targeted property fires. Diagnoses survivors as a bad mutant, bad oracle, bad workload, or bad property, and routes fixes back to antithesis-workload or antithesis-research." — [SKILL.md](https://github.com/antithesishq/antithesis-skills/blob/main/antithesis-mutation-testing/SKILL.md)
- Baseline gate: "A green baseline at the current code state is required before any mutant is designed. Mutation testing on a buggy SUT measures nothing". — [SKILL.md](https://github.com/antithesishq/antithesis-skills/blob/main/antithesis-mutation-testing/SKILL.md)
- Vacuity of green safety properties: "A green safety property is only *negative* evidence — the vacuous pass this skill exists to rule out". Unexercised assertions are scoped out as "outstanding — workload gap" when "`example_count` 0 in the baseline means the assertion never evaluated, and a mutant nothing reaches cannot be killed". — [SKILL.md](https://github.com/antithesishq/antithesis-skills/blob/main/antithesis-mutation-testing/SKILL.md)
- Anti-gaming rules: "A kill obtained by hobbling the workload into a narrow deterministic path, or by coarsening a mutant into obvious vandalism, is worse than an honestly-recorded un-killable candidate." "Re-keying an assertion to the mutant that will then validate it proves nothing — the re-swept kill is circular." — [SKILL.md](https://github.com/antithesishq/antithesis-skills/blob/main/antithesis-mutation-testing/SKILL.md)
- Collateral and dominance: properties other than the target that fail are "Collateral damage … credited only when the evidence shows a genuinely distinct violation"; a target always pre-empted by another property is "*outstanding — dominated*". — [SKILL.md](https://github.com/antithesishq/antithesis-skills/blob/main/antithesis-mutation-testing/SKILL.md); [sweep-and-verdicts.md](https://github.com/antithesishq/antithesis-skills/blob/main/antithesis-mutation-testing/references/sweep-and-verdicts.md)
- Earlier skills post (March 2026) covers research/setup/workload skills only; no mutation skill at that time [summary]. — [Sverre, Antithesis blog, 2026-03-25](https://antithesis.com/blog/2026/agent_skills/)

### Inferences
- The skill appears to have been added between the March 2026 skills post (which names three starter skills, none for mutation) and its 2026-09-23 version string; the blog post is 11 days older than this review. Any novelty statement has to be made relative to it.

## Q5. LLM-agent harnesses and LLM applications: deterministic simulation or record-replay testing, and does any of it use mutation or seeded defects?

### Takeaway
Record-replay tooling for agents is abundant and almost none of it validates its own checks. Two exceptions: Chronicle (arXiv, Sept 2026) runs first-order source mutants of agent tools under deterministic replay and classifies the survivors; AgentAssay (arXiv, March 2026) defines mutation operators over prompts, tools, models and context with a stochastic kill rule. I found no FoundationDB-style seeded simulation of an agent loop combined with source mutation.

### Cited Findings
- Chronicle [grep; abstract, contributions and evaluation passages read]: "records an agent run at its non-deterministic boundaries as immutable envelopes and replays it from the record" [summary quote]; "full replay issues zero model calls and is bit-stable across 20 repetitions". — [Chawla and Koul, "Chronicle: Cut-Point Replay for Regression Testing of LLM Agents", arXiv:2609.20625, 2026](https://arxiv.org/html/2609.20625)
- Chronicle's mutation study: "we generate all first-order mutants of each guarded tool with standard relational, logical, and constant mutation operators (192 in total); a mutant is killed when a test's verdict on it differs from its verdict on the unmutated fix. Cut-point tests kill 51; the full-stub baseline kills none". — [same](https://arxiv.org/html/2609.20625)
- Chronicle's survivor classification: "Of the 141 survivors, 110 cannot be killed by any test built from these recordings: they change code the recorded input never reaches, or change the guard without changing its decision on that input … The other 31 change output fields the assertion deliberately ignores … Among mutants that change behavior on the recorded input, cut-point tests thus kill 51 of 82 (62%). The unkillable mutants reflect a coverage limit of single-incident fixtures: each recording exercises one input." — [same](https://arxiv.org/html/2609.20625)
- Chronicle's own caveat: "Because the incidents, guards, and assertions were written together, these outcomes validate the mechanism on curated incidents rather than measure fault detection in general." Scope is 6 incidents. — [same](https://arxiv.org/html/2609.20625)
- AgentAssay [summary of arXiv abstract/HTML]: "We define four classes of agent-specific mutation operators ℳ={Mprompt,Mtool,Mmodel,Mcontext} … formalize the mutation score under stochastic semantics, and prove a mutation adequacy theorem"; "For AI agents, the 'source' comprises prompts, tool configurations, models, and context—requiring entirely new mutation operators." Verdicts are three-valued (Pass/Fail/Inconclusive) because runs are not deterministic. — [Bhardwaj, "AgentAssay: Token-Efficient Regression Testing for Non-Deterministic AI Agent Workflows", arXiv:2603.02601, 2026](https://arxiv.org/abs/2603.02601)
- muteval (hobby tool) [full, short post]: "muteval degrades the system (weakens a prompt rule, drops a retrieved doc, swaps in a weaker model), reruns your existing eval suite against each degraded version, and reports what fraction of those injected regressions your evals caught"; example "Mutation score: 33% (2/6 caught)". — [DEV Community post, 2026-07-22](https://dev.to/ashwin_ugale_102f2abc9cec/mutation-testing-but-for-llm-evals-early-experiment-would-love-feedback-2bl6)

### Inferences
- Chronicle is the closest prior art for the agent setting and already uses two of the claim's bins: "code the recorded input never reaches" (world gap) and "change the guard without changing its decision on that input" (equivalent on this corpus) are reported together as 110 unkillable, and "output fields the assertion deliberately ignores" (oracle tolerance) as 31. It merges the first two bins, has one recorded input per test instead of a seeded generator, and mutates only the guarded tool functions, not the agent loop.
- AgentAssay mutates agent artifacts, not harness source, and works under non-determinism; it is evidence that "mutation testing for agents" is a named topic, not that DST plus source mutation has been done for an agent loop.
