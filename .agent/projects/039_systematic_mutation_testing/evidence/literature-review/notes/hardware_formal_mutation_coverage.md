# Hardware and formal-verification precedents for judging a verification environment by injecting faults into the design

Reading-depth tags used below: **[full]** = full text read (or the first 30-45k characters of it, searched by keyword); **[partial]** = only the named passages of the full text were read; **[abstract]** = abstract only; **[summary]** = only Exa's machine summary or the title/metadata was seen, so nothing is asserted from it beyond what is marked. Raw Exa responses: `/workspaces/motoko_agent/tmp/research/exa_raw/hardware_formal_mutation_coverage/` (`sNN_*.json` searches, `cNN_*.json` full-text fetches).

Shorthand for the claim under review: three measurements per mutant on one seed — **R** (run reached the mutated code), **D** (run differed from the unmutated run), **K** (a check fired) — sorting mutants into *not reached* (world gap) / *reached, no difference* (equivalent on this corpus) / *differed, no check* (oracle gap) / *killed*.

## 1. Mutation-based functional qualification of RTL testbenches (Certess / SpringSoft / Synopsys Certitude) and its academic counterparts

### Takeaway
Yes: hardware verification has had exactly this four-way sort, under the names **Non-Activated / Non-Propagated / Non-Detected / Detected**, as a commercial product since 2007 (patent priority 2004), with the same three measurements (line executed; output differs from the same test without the fault; a checker fails) and the same readings (stimulus gap or dead code / observability gap or redundant code / checker gap). It was also applied to C/C++ models and embedded firmware by 2012.

- **The three conditions, stated by the tool's originator.** "To find a design bug, three things must occur during the execution of the verification environment: 1. - **The four classes, defined.** "A fault is considered "Activated" by a test if the line of design code containing the fault was executed at least once during the test. ### Inferences
- Certitude's NA / NP / ND / Detected is the claim's R / D / K sort, one for one. NA = not reached; NP = reached, no output difference against the same test and seed without the fault; ND = output difference, no checker failure. The readings also match: NA → stimulus or environment gap, or dead code; NP → more tests/seeds, more observation points, or "redundant code" (the equivalent-mutant reading); ND → checker (oracle) gap.
- Two differences from the claim. (a) Certitude compares at declared design outputs (movable observation points), not a whole-run trace, and Brownell says the NP/ND boundary is nothing but that declaration. (b) Practitioners read NP as a probable weakness first and as redundancy second; none of the sources read calls it "equivalent on this corpus".
- The activation measurement is taken once on the unmutated design (which test executes which fault's line), then used to schedule mutant runs. That is the same "coverage map from the reference run" optimisation the claim relies on.
- Bombieri et al.'s sentence "killed only if a testcase fails" is the published statement that functional qualification separates K from D, where classical mutation analysis treats an output difference as a kill.

### Gaps
- Hampton and Petithomme (2007) and the patent claims were not read in full, so the earliest document that prints the three status names is not pinned down; the earliest full text read that defines all four is DVCon 2012 (Bouvier et al.), and the three conditions appear in Hampton's 2009 brief.
- No Certitude user manual was found; the status names come from user papers and vendor slides.
- No source read states outright that the simulation must be deterministic for the NP comparison to be valid (see section 2).

## 2. Classical fault simulation: good machine against faulty machine, fault coverage

### Takeaway
Fault simulation (1960s onward) is the root of the method: run the same vectors on the fault-free and each faulty circuit and call a fault detected when outputs differ; fault coverage grades the test set. It has two of the three measurements as *conditions* (activation, propagation) but one *verdict*, because the tester's oracle is the good-machine response itself. ISO 26262 fault campaigns split the verdict again into observed versus detected, giving the same four classes as Certitude.

### Cited Findings
- **Definition by comparison.** "In fault simulation, test patterns are run with the "good" machine and every "bad" or faulty machine which has a line stuck at either a logical 0 or 1. If the output patterns of one bad machine and the good machine are different, the fault is said to have been detected." Concurrent simulation: "instead of recording the circuit status of all the bad machines, a concurrent fault simulator records the circuit status differences between every bad machine and the good machine" — Cheng and Yu, "Differential fault simulation - a fast method using minimal memory", DAC 1989 **[partial; read through Exa's full-text copy, raw file `c05_misc.json`; journal version: [J. Electronic Testing](https://link.springer.com/article/10.1007/BF00134011)]**.
- **What a fault simulator reports.** "A program that models a design with fault present. Inputs: A circuit, A sequence of test vectors, A fault model ... Determines Fault coverage (fault grading), Set of undetected faults (Areas of Low Fault Coverage)"; algorithms listed: "Serial Parallel Deductive Concurrent" — M. Tahoori, "Testing Digital Systems I, Lecture 6: Fault Simulation" (2010), [KIT slides](https://cdnc.itec.kit.edu/downloads/06_Fault_Simulation.pdf) **[partial]**. Purpose: "To evaluate the quality of a test set - i.e., to compute its fault coverage" — S.-Y. Huang, [NTHU lecture notes ch. 3](https://www.ee.nthu.edu.tw/~syhuang/testing/ch3.fault_simulation.pdf) **[partial]**.
- **Undetectable faults are the equivalent-mutant analogue.** "the well-known concepts of redundancy and undetectability of a stuck-at fault, which are equivalent in combinational circuits, are not equivalent in sequential circuits" — Abramovici and Breuer, "On Redundancy and Fault Detection in Sequential Circuits", IEEE Trans. Computers 28(11), 1979, [ACM DL](https://dl.acm.org/doi/10.1109/TC.1979.1675267) **[abstract]**.
- **Functional-safety fault campaigns separate observation from detection.** "fault simulator inserts the faults to create the faulty model or bad machine. Test pattern ... is applied and the output at the observation points (defined by user) from faulty machine is compared with that of the good machine and in case there is divergence from the actual behavior the fault is termed to be observed. Once observed, the fault is expected to hit the diagnostic point or the detection point which is the safety mechanism". Faults "observed at the observation point ... but ... not caught by the safety mechanism, are the dangerous undetected faults"; a fault "neither observed at the observation points nor detected by the safety mechanism ... needs manual analysis"; "Verification engineer needs to go and do manual analysis of each and every fault that is not observed by the fault simulation to make sure the fault was not observed because of the nature of the design and not due to non exhaustivity of the simulation environment." — Ahuja (Synopsys), Agarwal (NXP), Jana (Synopsys), "Formal Assisted Fault Campaign for ISO26262 Certification", [DVCon archive](https://dvcon-proceedings.org/wp-content/uploads/formal-assisted-fault-campaign-for-iso26262-certification.pdf) **[partial; year not verified]**.
- Four-class lists "Not Activated / Not Controlled; Not Observed / Not Propagated; Observed but Not Detected; Detected" appear in da Silva, Bagbaba, Hamdioui, Sauer, "Use of Formal Methods for verification and optimization of Fault Lists in the scope of ISO26262", [DVCon archive](https://dvcon-proceedings.org/wp-content/uploads/Use-of-Formal-Methods-for-verification-and.pdf) **[summary only: the class names come from Exa's summary; my keyword read of the slide text did not locate them]**.

### Inferences
- A deterministic simulator is what makes "same vectors, compare outputs" meaningful; every definition above presupposes it without saying so. Concurrent and differential simulation go further and store only the *difference* between faulty and good machine state, which is the D measurement taken at every node and time step.
- In manufacturing test there is no separate K: the expected response is the good machine's output, so "differs at an observed output" *is* "detected". The three-way split only appears when the judge is something weaker than a full output comparison — a testbench checker (Certitude) or a safety mechanism (ISO 26262).
- The ISO 26262 "not observed" class carries the same ambiguity the claim labels "equivalent on this corpus": Ahuja et al. say each such fault must be analysed to tell design-inherent masking from non-exhaustive stimulus.

### Gaps
- Abramovici, Breuer and Friedman's textbook was not readable online (publisher and archive pages only); definitions of fault coverage, fault efficiency and the D-algorithm's activation/propagation conditions are therefore taken from lecture slides, not the book.
- No source read states the determinism requirement explicitly. Query s23 returned only general papers on UVM/SystemVerilog random stability, none tying seed stability to mutation or fault-injection validity.

## 3. Observability-based coverage (Devadas-Ghosh-Keutzer 1996; OCCOM 1998/2001)

### Takeaway
Observability-based coverage (1996) added the second measurement to code coverage: a statement counts only if a perturbation there (a "tag") would reach an output under the given stimulus. It has no third measurement and injects no real mutants; it was carried over to software in 2000 (embedded C) and 2013 (Observable MC/DC).

### Cited Findings
- "Our metric computes observability information to determine whether effects of errors that are activated by the program stimuli can be observed at the circuit outputs." — Devadas, Ghosh, Keutzer, "An observability-based code coverage metric for functional simulation", ICCAD 1996, [IEEE Xplore](https://ieeexplore.ieee.org/document/569832) **[abstract]**.
- "Coverage metrics ... should compute statement execution counts (controllability information) and check to see whether effects of possible errors activated by program stimuli can be observed at the circuit outputs (observability information). ... it breaks up the computation into two phases: functional simulation of a modified HDL model followed by analysis of a flowgraph extracted from the HDL model." — Fallah, Devadas, Keutzer, "OCCOM: efficient computation of observability-based code coverage metrics for functional verification", DAC 1998, [ACM DL](https://dl.acm.org/doi/10.1145/277044.277078); journal version IEEE TCAD 2001 **[abstract of the TCAD version]**.
- **Transfer to software, 2000.** "Motivated by recent work on observability-based coverage metrics for models described in a hardware description language, we develop a method that computes an observability-based code coverage metric for embedded software written in a high-level programming language. Given a set of input vectors, our metric indicates the instructions that had no effect on the output. An assignment that was not relevant to generate the output value cannot be considered as being covered." — Costa, Devadas, Monteiro, "Observability analysis of embedded software for coverage-directed validation", ICCAD 2000 **[abstract; read through Exa's copy]**; later journal paper: Costa and Monteiro, [ACM TODAES 2013](https://dl.acm.org/doi/10.1145/2442087.2442090) **[summary only]**.
- **Transfer to software, 2013.** "MC/DC adequate tests would frequently exercise faulty code, but the effects of the faults would not propagate to the monitored oracle variables. In this report, we combine the MC/DC coverage metric with a notion of observability that helps ensure that the result of a fault encountered when covering a structural obligation propagates to a monitored variable" — Whalen, Gay, You, Heimdahl, Staats, "Observable Modified Condition/Decision Coverage", ICSE 2013 **[abstract; read through Exa's copy; that it builds on the Devadas/Fallah tagging work is from Exa's summary only]**.

### Inferences
- OCCOM supplies R and an *estimate* of D (tag propagation is conservative analysis on the unmutated run, not a comparison of two runs). It says nothing about K: it assumes whatever reaches an output is checked.
- Functional qualification can be read as OCCOM with real mutants plus the checker question. Lisherness and Cheng (section 1) present the three as one progression.

### Gaps
- OCCOM's full text was not read; how tags are defined and where they over- or under-approximate real propagation is not recorded here.
- Tasiran and Keutzer, "Coverage metrics for functional validation of hardware designs" (IEEE Design & Test, 2001) was found (s24) but seen as summary only.

## 4. Mutation coverage and vacuity in model checking

### Takeaway
Model checking defined coverage by mutation in 1999 (flip a signal in a state; if the property still holds the state is uncovered) and vacuity by mutating the specification (1997); Kupferman (2006) states the two are the same check on different inputs, and Kupferman, Li and Seshia (2008) prove a duality. These give one measurement per mutant (does verification still pass), not three.

### Cited Findings
- **Vacuity, 1997.** Beer, Ben-David, Eisner, Rodeh, "Efficient detection of vacuity in ACTL formulas", CAV 1997, [doi:10.1007/3-540-63166-6_28](https://doi.org/10.1007/3-540-63166-6_28); journal version FMSD 18(2):141-162, 2001 **[summary only; no abstract retrievable]**. As reported by Ball and Kupferman: "In [3], Beer et al. suggested a first formal treatment of vacuity. As described there, vacuity is a serious problem: "our experience has shown that typically 20% of specifications [quotation cut off in the text read]" — [Ball and Kupferman 2008](https://www.cs.huji.ac.il/~ornak/publications/tap08.pdf) **[full]**. Example: "the specification ϕ = G(req → F grant) is vacuously satisfied in a system in which req is always false" — [CKKV 2001](https://doi.org/10.1007/3-540-44585-4_7) **[full: first 40k chars via Exa's copy]**.
- **Coverage by mutation, 1999.** "Although model checking is an exhaustive formal verification method, a bug can still escape detection if the erroneous behavior does not violate any verified property. We propose a coverage metric to estimate the "completeness" of a set of properties ... We uncovered several coverage holes including one that eventually led to the discovery of a bug that escaped the initial model checking effort." Definition: "A covered set of states for an observed signal is the set of reachable states in which the values of the observed signal must be checked to prove satisfaction of the property. ... if we change the value of the observed signal in any state of the model outside the covered set, the property should still be satisfied. ... if we change the value of the observed signal in any covered state, the property should fail. ... To determine whether a state belongs in the covered set, we modify the value of the observed signal in that state and assess its effect on the validity of the property." — Hoskote, Kam, Ho, Zhao, "Coverage estimation for symbolic model checking", DAC 1999, [doi:10.1145/309847.309936](https://doi.org/10.1145/309847.309936) **[full: via Exa's copy]**.
- **Chockler, Kupferman, Vardi, TACAS 2001.** "Coverage metrics are based on modifications we apply to the system in order to check which parts of it were actually relevant for the verification process to succeed. We introduce two principles ...: a distinction between state-based and logic-based coverage, and a distinction between the system and its environment." — "Coverage Metrics for Temporal Logic Model Checking", [doi:10.1007/3-540-45319-9_36](https://doi.org/10.1007/3-540-45319-9_36) **[partial: abstract and introduction via Exa's copy]**.
- **Chockler, Kupferman, Kurshan, Vardi, CAV 2001.** "We can say that in testing, a state is "uncovered" if it is not essential to the success of the testing procedure. The similar idea can be applied to model checking, where the state is defined as "uncovered" if its labeling is not essential to the success of the model checking process. This approach was first suggested by Hoskote et al." "Intuitively, if a part of the system can be changed without violating the specification, this part is uncovered by the specification. Formally, for a Kripke structure K, a state w in K, and an observable signal q, the dual structure K_{w,q} is obtained from K by flipping the value of q in w ... Hoskote et al. define the set q-cover(K, ϕ) as a set of states w such that K_{w,q} does not satisfy ϕ." Reading of low coverage: "One possibility is that the specification is not complete enough ... Another possibility is that the system contains redundancies." — "A Practical Approach to Coverage in Model Checking", [doi:10.1007/3-540-44585-4_7](https://doi.org/10.1007/3-540-44585-4_7) **[full: first 40k chars via Exa's copy]**.
- **The stated duality, 2006.** "Two leading sanity checks are vacuity and coverage. In vacuity, the goal is to detect cases where the system satisfies the specification in some unintended trivial way. In coverage, the goal is to increase the exhaustiveness of the specification by detecting components of the system that do not play a role in verification process. ... we argue that, in many aspects, the two checks are essentially the same: both are based on repeating the verification process on some mutant input. In vacuity, mutations are in the specifications, whereas in coverage, mutations are in the system." — Orna Kupferman, "Sanity Checks in Formal Verification", CONCUR 2006, [Springer](https://link.springer.com/chapter/10.1007/11817949_3) **[abstract]**.
- **Duality formalised, 2008.** "Both checks involve mutations to the specification or the circuit implementation. ... Since faults can be viewed as mutations, our theory of mutations can also be used in a formal approach to fault injection." — Kupferman, Li, Seshia, "A theory of mutations with applications to vacuity, coverage, and fault tolerance", FMCAD 2008, [ACM DL](https://dl.acm.org/doi/10.5555/1517424.1517449) **[abstract]**. Companion text: "Many mutations correspond to actual faults, such as ones in which signals are ignored, flipped, delayed, or stuck at a value ... the low coverage of I by S, which causes I_µ to satisfy S, is related to the vacuous satisfaction of S in I, which causes I to satisfy S_µ̃." — Kupferman, Li, Seshia, "On the Duality between Vacuity and Coverage" **[abstract; read through Exa's copy; canonical URL not resolved]**.
- **Ball and Kupferman, 2008.** "In the context of model checking, this can be done by analyzing the effect of applying mutations to the specification or the system. If the system satisfies the mutated specification, we know that some elements of the specification do not play a role in its satisfaction, thus the specification is satisfied in some vacuous way. If the mutated system satisfies the specification, we know that some elements of the system are not covered by the specification. Coverage in model checking has been adopted from the area of testing ... It is now time for model checking to pay back, and let testing enjoy the rich theory and applications of vacuity." Three settings; for run-time monitors: "a test suite passes vacuously if it passes also with a monitor with fewer transitions"; for software: "T passes S vacuously in P if some branch of S does not affect its pass" — "Vacuity in Testing", TAP 2008, [Springer](https://link.springer.com/chapter/10.1007/978-3-540-79124-9_2), [author PDF](https://www.cs.huji.ac.il/~ornak/publications/tap08.pdf) **[full]**.

### Inferences
- Because model checking explores all behaviours, R is vacuous (only reachable states are considered) and there is no separate D: "the mutant still satisfies the specification" merges "no difference" with "difference the specification does not see". CKKV's two readings of low coverage — incomplete specification or redundant system — are those two cases, left for the user to tell apart.
- Vacuity is the complementary check the claim does not mention: mutate the *oracle* (property, monitor, invariant) and see whether the suite still passes. Ball and Kupferman's monitor definition applies directly to DST invariants over traces.
- Certitude's formal mode (section 1) is where the two lines meet: NA becomes "outside every property's cone of influence", ND becomes "all properties still proven".

### Gaps
- Beer et al.'s own definition of vacuity and the full "20%" sentence were not read at source.
- Kupferman 2006 and Kupferman-Li-Seshia 2008 were read as abstracts only.
- Later computational work (Chockler, Kroening, Purandare on mutation coverage with interpolation, 2010-2012) was not searched.

## 5. Transfer to software testing of real implementations

### Takeaway
There are several documented transfers, but each carries one piece: observability coverage (2000, 2013), vacuity (2008), model-checking coverage recast as program mutation for C verification harnesses (2015/2018), ATPG ideas for equivalent mutants (2016), and Certitude itself run on C firmware (2012) and C/C++ models. One paper found applies the full activate / propagate / detect sort to software tests by comparing an unmutated and a mutated run (Große et al., 2016), on virtual-prototype models. No source found connects any of this to deterministic simulation testing.

### Cited Findings
- **Certitude on software.** Embedded C firmware, with all four statuses reported (section 1) — [Bouvier et al., DVCon 2012](https://dvcon-proceedings.org/wp-content/uploads/a-practical-approach-to-measuring-and-improving-the-functional-verification-of-embedded-software.pdf) **[full]**. "Certitude can measure and help to improve all aspects of functional verification quality at different levels of abstraction, including HDL and C/C++/SystemC languages" — [DATE 2015 University Booth entry, "Certitude-C/C++"](https://past.date-conference.com/date15/content/certitude-cc-functional-qualification-tool-fault-injection-ccsystemc-models) **[full: 800-char notice]**.
- **The closest match to the three-measurement sort, applied to software tests.** Mutants are placed only in code "marked as covered in the code coverage report ... Essentially, this gives us the activation of the mutation". Then: "1) Generate coverage report for original IP running current test suite 2) Mutate IP using a fault model 3) Generate coverage report for mutated IP 4) Analyze consistency of coverage results and software test result". Table I, with coverage change between the two runs standing for "propagate" and the software test verdict for "detect": "C1 Fluctuate / Fail / Adequate test; C2 Fluctuate / Pass / Weak detection by SW test; C3 Stable / Fail / Propagation path missing; C4 Stable / Pass / Propagation/detection problem". The paper says it elevates "the main concepts of mutation-based qualification to the context of SDV" and relates its steps "to the main qualification tasks (activate, propagate, detect)" — Große, Le, Hassan, Drechsler, "Guided Lightweight Software Test Qualification for IP Integration using Virtual Prototypes", ICCD 2016, [author PDF](https://agra.informatik.uni-bremen.de/doc/konf/2016ICCD_SWTestQualificationIPVP.pdf) **[partial]**.
- **Model-checking coverage recast for real C code.** "The problem of checking verification results has concerned the model checking community for some time, and resulted in efforts to define coverage metrics for model checking [54, 23]. While such metrics are interesting and useful, they have typically been aimed at hardware verification, and most useful to experts in formal verification. In this paper, we adapt traditional mutation testing [18, 64] to the problem of software verification." Applied with CBMC to "a routine in Mozilla's JavaScript engine" and "the Linux kernel Read-Copy-Update (RCU) mechanism"; the tools generate tests that "1) fail to kill a mutant but 2) cover the mutated code, in order to facilitate understanding of the limits of a harness"; and, citing property mutation, "we, following this line of thought, propose the developer mutate the test harness itself". Reference list includes Hoskote et al. 1999, CKKV 2001 and Kupferman-Li-Seshia 2008 — Groce, Ahmed, Jensen, McKenney, Holmes, "How Verified (or Tested) is My Code? Falsification-Driven Verification and Testing", Automated Software Engineering (journal), 2018; conference version ASE 2015, [author PDF](https://agroce.github.io/asej18.pdf) **[full: first 45k chars]**.
- **Vacuity for testing** — Ball and Kupferman 2008 (section 4) **[full]**. Its software setting is a terminating procedure and a Boolean checker in "a simple programming language"; no experiment on a real code base appears in the passages read.
- **Observability coverage for software** — Costa, Devadas, Monteiro 2000 **[abstract]** and Whalen et al. 2013 **[abstract]** (section 3). Whalen et al. evaluate on "four subsystems from the civil avionics domain and the control logic of a microwave".
- **ATPG ideas for equivalent mutants.** "the notion of a mutation in software testing is very similar to the notion of a fault in hardware testing ... we propose the first approach for local analysis in software testing to identify mutants that are undetectable" — Zhang and Gupta, "Using hardware testing approaches to improve software testing: Undetectable mutant identification", 2016 **[abstract; read through Exa's copy; venue and DOI not resolved]**.
- **Software research with the same three measurements, origin not established.** "For every mutated test run, we are able to determine: (a) if the mutation induced a state infection; (b) if the infection propagated through the end of the test run; and (c) if the test failed in the presence of a propagated infection. ... a propagated infection does not always reveal itself as a test failure. We also find that a significant portion of survived mutants in our study could have been killed by observing propagated state infections that were left undetected." (1.1 million mutated test runs, 43,000 mutations) — Du, Palepu, Jones, "Ripples of a Mutation - An Empirical Study of Propagation Effects in Mutation Testing", ICSE 2024, [doi:10.1145/3597503.3639179](https://doi.org/10.1145/3597503.3639179) **[abstract]**. Also seen as summary only: Vera-Pérez, Danglot, Monperrus, Baudry, "Suggestions on Test Suite Improvements with Automatic Infection and Propagation Analysis" (2019), and Yao, Harman, Jia, "A study of equivalent and stubborn mutation operators using human analysis of equivalence" (ICSE 2014) **[summary only; flagged for the researchers covering software oracle metrics]**.

### Inferences
- The hardware community treats its method as borrowed from software (Hampton 2009 and Brownell 2013 both cite software mutation analysis as the origin) and what it added is the activation/propagation/detection instrumentation and the industrial workflow. The software community has its own reach/infect/propagate vocabulary, so the classification reached software by two routes, and I did not find a software paper on ordinary application code that names functional qualification or Certitude as its model. Whether Du et al. or Vera-Pérez et al. cite hardware work was not checked in their texts.
- What the precedents do not contain: a seeded, simulated *environment* (network, clock, disk, fault schedule) as the stimulus generator, or whole-trace comparison of mutated against unmutated runs. RTL testbenches with constrained-random stimulus and fixed seeds are the nearest analogue, and Brownell's "adding more seeds" remedy for NP is the same move as widening a DST seed corpus.

### Gaps
- Queries s18 and s26 looked for a software-testing paper that cites functional qualification or model-checking coverage as its model and classifies survivors three ways; apart from Große et al. (hardware-adjacent) and Groce et al. (kill/cover only) none was found. This is absence in about two searches, not proof of absence.
- No search was run pairing "deterministic simulation testing" with mutation; that belongs to other researchers' scope.

## 6. How close each precedent is to the three-measurement classification

### Takeaway
The classification itself is not new: functional qualification has R, D and K as separate measurements with the same four classes and the same readings, documented from 2007-2013 and sold commercially since 2007. The other precedents each hold a subset.

### Cited Findings
- Functional qualification (Certitude), 2004 priority / 2007 product: R = line executed in the unmutated run; D = output differs from "the same test with no fault inserted"; K = a test fails. Classes NA / NP / ND / Detected — [Brownell 2013](https://dvcon-proceedings.org/wp-content/uploads/whos-watching-the-watchmen-the-time-has-come-to-objectively-measure-the-quality-of-your-verification-environment.pdf), [Bouvier et al. 2012](https://dvcon-proceedings.org/wp-content/uploads/a-practical-approach-to-measuring-and-improving-the-functional-verification-of-embedded-software.pdf). **Match: complete.**
- ISO 26262 fault campaigns: D at observation points, K at detection points (safety mechanism), plus not-activated/not-observed classes — [Ahuja et al.](https://dvcon-proceedings.org/wp-content/uploads/formal-assisted-fault-campaign-for-iso26262-certification.pdf). **Match: same structure; the faults are physical and the "check" is part of the design, so it grades the design's safety mechanism, not the test environment.**
- Classical fault simulation: D only, and D is the verdict — [Cheng and Yu 1989](https://link.springer.com/article/10.1007/BF00134011). **Match: one measurement; supplies the good-versus-faulty comparison and the undetectable-fault concept.**
- Observability-based coverage: R plus an analytic estimate of D, no K, no real mutants — [Fallah et al. 1998](https://dl.acm.org/doi/10.1145/277044.277078). **Match: two of three.**
- Mutation coverage in model checking: one verdict per mutant (specification still satisfied), which merges "no difference" and "unseen difference" — [CKKV 2001](https://doi.org/10.1007/3-540-44585-4_7). Vacuity: the same check with the oracle mutated — [Kupferman 2006](https://link.springer.com/chapter/10.1007/11817949_3). **Match: one of three, plus a dual check the claim lacks.**
- Software carry-over: Große et al. 2016 has all three on SystemC/C++ models driven by software tests — [ICCD 2016](https://agra.informatik.uni-bremen.de/doc/konf/2016ICCD_SWTestQualificationIPVP.pdf); Du et al. 2024 measure infection, propagation and test failure on software at scale — [ICSE 2024](https://doi.org/10.1145/3597503.3639179).

### Inferences
- If the claim is "determinism lets mutation take three measurements per mutant and sort survivors four ways", hardware verification did that first and says why in nearly the same words. A defensible residue is narrower: applying it where the stimulus is a seeded simulated world for production software, with D taken over the whole trace, and naming the NP class "equivalent on this corpus". None of the sources read does those things, but that was not searched for directly here.
- Hardware practice is a caution about the claim's label for the second class: Brownell reports that NP faults "often indicate missing tests" and are reduced by more seeds or more observation points, while one vendor case study attributes its two residual NP faults to "redundant code". The sources read give no ratio between the two readings.
