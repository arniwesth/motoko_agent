## 1. How were controlled-scheduling, model-checking and simulation tools for concurrent and distributed systems evaluated? Did any use mutation analysis or seeded defects as ground truth? Which benchmarks exist?

### Takeaway
The dominant evaluation is "new bugs found in real systems" plus "time to reproduce known bugs"; mutation analysis in the operator-generated sense is essentially absent from the systems-venue tool papers I examined. What does recur is a small set of hand-seeded or flag-re-introduced bugs used as a fixed target to compare schedulers (P# at FAST 2016, taPCT, ModelFuzz, two TU Delft theses), and Gligoric et al. (ISSTA 2013) name exactly this gap: concurrency testing techniques "have been mostly evaluated using programs with a small number of real or manually seeded concurrency bugs".

## 2. Mutation operators for concurrency, actors and distributed protocols, and how kills are judged under nondeterminism

### Takeaway
Concurrency mutation operators are well developed for shared-memory Java/C (Delamaro 2001, Bradbury 2006, Gligoric 2013, CCmutator), and exist for actors (Jagannath 2010, μAkka 2023), Erlang/Elixir and MPI; I found none aimed at production distributed protocol code such as Raft or Paxos implementations. The kill criterion under nondeterminism has been formalised since the 1990s, and three families of answers exist: force the mutant onto a recorded synchronization sequence (Carver's DEMT, 1993), compare sets of outputs over many or all schedules (Offutt's MET; Gligoric 2013), or explore mutants inside a model checker that controls the scheduler (MuTMuT on Java PathFinder, 2010).

## 3. Nondeterminism as an obstacle to mutation testing, and deterministic execution as the remedy

### Takeaway
This is old and explicit. Carver (1993) names nondeterminism as the problem and defines Deterministic Execution Mutation Testing; MuTMuT (2010) runs mutation testing inside a scheduler-controlling model checker and reuses per-mutant reachability recorded on the unmutated exploration; Shi, Bell and Marinov (2019) quantify what uncontrolled nondeterminism does to ordinary mutation scores. The strongest counterpoint to the claim's "same seed" measurement is also in this literature: Gligoric et al. argue that running "the same schedules" on mutant and original "cannot be done" in general, because the mutation can enable or disable schedules.

### Cited Findings
- **Carver 1993, the earliest statement.** "Mutation-based testing has been applied to sequential software; however, problems are encountered when it is applied to concurrent programs. These problems are a product of the nondeterminism inherent in the executions of concurrent programs. In this paper, we describe a general approach to testing and debugging concurrent programs, called deterministic execution testing and debugging. We then describe a combination of deterministic execution testing and mutation-based testing, called deterministic execution mutation testing (DEMT)". R. Carver, "Mutation-based testing of concurrent programs", Proc. IEEE International Test Conference, 1993. [abstract] — [Exa copy](https://exa.ai/library/publication/8dyvsfm9v9d) (IEEE DOI not fetched)
- **How DEMT judges a kill (secondary description).** "Carver (1993) defined an approach using MET and DET -called Deterministic Execution Mutation Testing (DEMT) -in which the mutant is run deterministically. MET is used to generate different synchronization sequences of the original program. A pair {input, synchronization} is considered as test input and is applied to both original and mutant program. The mutant is forced to run a synchronization sequence, and it is killed if it cannot run the synchronization sequence or the result was different from the original". Silva thesis, 2018. [KWIC] — [Exa copy](https://exa.ai/library/publication/1h68twm5706)
- **Known weaknesses of the non-deterministic alternative.** Of Offutt et al.'s multiple-execution approach: "This approach has the problem of mutants that can be erroneously killed, once it is not guaranteed that all possible outputs of the original program were found using MET. Another problem is related to mutants that remain alive because the synchronization sequence followed is not capable of showing the presence of the defect." Silva thesis, 2018. [KWIC] — [Exa copy](https://exa.ai/library/publication/1h68twm5706)
- **MuTMuT: mutation testing under a controlled scheduler, with reachability recorded on the original run.** Implemented "in Java PathFinder (JPF) ... JPF implements a backtrackable Java Virtual Machine (JVM) that provides control over nondeterministic choices including thread schedules." The original exploration records "a set of reached (live) mutants and the additional information", then "performs a special exploration ... of the test on each of those mutants. If the test fails, the mutant is killed." Pruning is sound on reachability: "it is not necessary to explore whether test1 can kill Mutant1 if the first executed operation is withdraw, since no such execution reaches the mutation"; "since the pruned part of the state space does not reach the mutant, OneState is still guaranteed to correctly find whether the mutant is killed"; and "the same strategy has to be used for both the original and mutant explorations." Gligoric, Jagannath, Marinov, "MuTMuT: Efficient Exploration for Mutation Testing of Multithreaded Code", ICST 2010. [KWIC] — [author PDF](https://mir.cs.illinois.edu/marinov/publications/GligoricETAL10MuTMuT.pdf); [IEEE](https://ieeexplore.ieee.org/document/5477101/). Journal version: Gligoric, Jagannath, Luo, Marinov, "Efficient mutation testing of multithreaded code", STVR 2013, 12 programs, five techniques. [abstract] — [Exa copy](https://exa.ai/library/publication/t9cx8f1g8vz)
- **The counterpoint: same schedule on mutant and original is not always possible.** "it may fail to detect that a mutant is killed (false negative) if a schedule that would lead to a different output is never executed in the mutated code. Also, it may report that a mutant is killed when this should not be the case (false positive) if a different output is obtained on the mutated code than on the original code. While it may seem that false positives can be avoided by running the same schedules on the mutated and original code, note that this cannot be done [10]. First, in theory, it may be impossible to enforce the execution of the same schedules in the original and mutated run because the changes in the mutant may enable or disable some schedules (e.g., grabbing some locks that prevent threads from executing or releasing some locks that allow other threads to execute). Second, in practice, it is very hard to tightly control the scheduler for larger programs where the execution can depend on real time, as is the case for some of our experiments". Gligoric et al., ISSTA 2013. [KWIC] — [author PDF](https://users.ece.utexas.edu/~gligoric/papers/GligoricETAL13Comutation.pdf). The same paper determined kills "using stress runs or JPF for each subject" and warns that "the precise numbers of hit and killed mutants may differ because of false positives and false negatives."
- **Simulation nondeterminism forces assertion-based kills.** "In most mutation analyses, the exact output from the original version is used as an oracle against which mutant output is compared. This is not always possible with simulation-based testing because simulations of distributed systems are naturally nondeterministic. In practice, we use assertions and sanity checks in the simulation code to determine which results are considered 'reasonable.'" Rutherford, Carzaniga, Wolf, TSE 2008. [KWIC] — [TSE PDF](https://www.inf.usi.ch/carzaniga/papers/rcw_tse08.pdf)
- **Survey position.** "In the case of non-deterministic systems, it is necessary to define mutant killing conditions based on a form of oracle that models the behaviour of the obtained outputs. Patrick et al. [213] use pseudo-oracles to test stochastic software. Rutherford et al. [214] use discrete-event simulations (executable specifications) to define assertions and sanity checks". Papadakis, Kintis, Zhang, Jia, Le Traon, Harman, "Mutation Testing Advances: An Analysis and Survey", Advances in Computers, 2019. [KWIC; a search of the 294k-character text for "determinis", "flak" and "concurren" returned this passage and tool-table rows only, so the survey does not treat deterministic execution as a remedy] — [survey PDF](https://mutationtesting.uni.lu/survey.pdf)
- **Measured cost of nondeterminism in ordinary mutation testing.** "Traditional mutation testing implicitly assumes that test behavior is deterministic while rerunning the same tests on different mutants. If a test can have different outcomes when run on the same mutant, then it is unclear if the test actually kills the mutant. In particular, if a test has non-deterministic coverage, a mutant can appear 'killed' by a test in the ..."; "mutation scores vary by four percentage points on average between repeated executions, and 9% of mutant-test pairs have an unknown status"; "about 4% of mutants are unknown". Remedy proposed: "strategically re-running tests" and isolation, not deterministic execution. Shi, Bell, Marinov, "Mitigating the Effects of Flaky Tests on Mutation Testing", ISSTA 2019. [KWIC] — [ACM](https://dl.acm.org/doi/10.1145/3293882.3330568)
- **Related flakiness results [summary]:** about 19% of mutants killed by flaky tests were killed by the flakiness itself (Alshammari, Ammann, Hilton, Bell, 2024) — [Exa copy](https://exa.ai/library/publication/wbvgmfx376r); FlakiMe (Cordy, Rwemalika, Franci, Papadakis, Harman, ICSE 2022) — [Exa copy](https://exa.ai/library/publication/yg7q1zpryk2); "Test Flimsiness: Characterizing Flakiness Induced by Mutation to the Code Under Test", ICSE 2026 — [ACM](https://dl.acm.org/doi/10.1145/3744916.3773125).
- **Reach / infect / propagate / reveal classification of survivors, done by comparing mutant and original runs (sequential code).** Reneri determines "which of the following three reasons prevent the detection of the extreme transformation is: the test inputs are not sufficient to infect the state of the program; the infection does not propagate to the test cases; the test cases have a weak oracle that does not observe the infection", by observing "runtime differences between test runs on the original and the transformed method"; "For 63% of the cases, the existing test cases can infect the program state, meaning that undetected transformations are mostly due to observability and weak oracle issues." Vera-Pérez, Danglot, Monperrus, Baudry, "Suggestions on Test Suite Improvements with Automatic Infection and Propagation Analysis", 2019. [abstract] — [arXiv:1909.04770](https://arxiv.org/abs/1909.04770). Du, Palepu, Jones, "Ripples of a Mutation — An Empirical Study of Propagation Effects in Mutation Testing", ICSE 2024: over 43,000 mutations and 1.1 million test runs; "once state infection is observed, propagation is frequently detected; however, a propagated infection does not always reveal itself as a test failure"; "approximately 18.5%-89.4% of surviving mutants could potentially be killed based on infection or propagation information." [KWIC] — [ACM](https://dl.acm.org/doi/10.1145/3597503.3639179)

### Inferences
- Part (b) of the claim has two separable halves, and each has prior art. "Run the mutant deterministically against the original's recorded execution" is DEMT (1993) and MuTMuT (2010). "Sort survivors into not-reached / no-difference / difference-not-checked / killed by comparing against the unmutated run" is the RIP/RIPR model, operationalised by Reneri (2019) and Ripples (2024) for JUnit-style tests. What I did not find is the two combined on a seeded simulation of a distributed system, with the trace as the compared object and named invariants as the oracle.
- Gligoric et al.'s objection applies to forcing an identical thread schedule. A seeded simulator sidesteps the "cannot enforce" half (any seed yields a legal run of the mutant) but not the underlying issue: once the mutant changes which events are enabled or how many random draws are consumed, the same seed no longer denotes the same schedule, so "the run differed from the unmutated run" can be true for reasons unrelated to the mutated logic's effect on outcomes. The literature gives no measurement of how often that happens; this is my inference, not a sourced fact.
- MuTMuT's "reached mutants recorded during the original exploration" is the claim's first measurement (did the run reach the mutated code) obtained without running the mutant at all.
- The flaky-test line of work treats nondeterminism as noise to be averaged out by reruns. None of the flaky-mutation papers I read proposes deterministic execution as the fix.

### Gaps
- Carver 1993 was read only as an abstract; the DEMT kill rule is quoted from Silva's 2018 thesis, a secondary source.
- Offutt et al. 1996 (MET), Silva-Barradas 1998 and Delamaro 2001 were not retrieved.
- No source found that states, for a seeded deterministic simulator specifically, whether same-seed comparison of mutant and original is sound. Queries q13, q23, q24, q25 found no academic paper on it.

## 4. Validation of trace and history checkers by mutating histories or implementations

### Takeaway
I found no checker paper that validates itself by mutation analysis of implementations or by systematically mutated histories. Elle is evaluated on real databases; Lowe's linearizability tester on bugs that arose in his own implementations; newer isolation checkers add synthetic histories.

### Cited Findings
- **Elle.** The stated goal is a checker that is "sound (no false positives), efficient ..., effective (finding violations in real databases)"; keyword search of the full arXiv text for mutat/seeded/synthetic/injected-anomaly/ground-truth found no evaluation of that kind, only the fault-injection sentence in the introduction and the Knossos runtime comparison. Lowe, "Testing for linearizability", Concurrency and Computation: Practice and Experience, published online December 2016. ## 5. Use of a fixed set of mutants to compare schedulers, fault-injection policies or workload generators

### Takeaway
Using mutants as the yardstick for comparing analysis techniques on concurrent code dates to Bradbury, Cordy and Dingel (2007, ConTest vs Java PathFinder). For input generators it is current practice outside distributed systems (Etna for property-based testing, mutation analysis for fuzzers). For schedulers and fault-injection policies in distributed systems the fixed set is a handful of hand-seeded bugs, not mutants. The one artefact I found that grades a deterministic simulation harness and its individual oracles against a set of planted defects is an unreviewed 2026 GitHub repository.

### Cited Findings
- **Mutants to compare a concurrency tester with a model checker (2007).** "Using program mutation, the assessment method creates a range of faulty versions of a program and then evaluates the ability of various testing and formal analysis tools to detect these faults. The approach is implemented and automated in an experimental mutation analysis framework (ExMAn) ... we present the results of a comparison of testing using the IBM tool ConTest and model checking using the NASA tool Java PathFinder (JPF)." Bradbury, Cordy, Dingel, "Comparative Assessment of Testing and Model Checking Using Program Mutation", TAIC PART-MUTATION 2007. [abstract] — [ACM](https://dl.acm.org/doi/10.5555/1308173.1308285)
- **Mutants to rank test suites and adequacy criteria for distributed systems (2006/2008).** Engineers "select multiple adequate test suites, use fault-based analysis to relate the suites by mutant score, and apply the highest scoring suite to the implementation." Rutherford, Carzaniga, Wolf, TSE 2008. [KWIC] — [TSE PDF](https://www.inf.usi.ch/carzaniga/papers/rcw_tse08.pdf)
- **Mutants as ground truth for generators (property-based testing).** "We opt for manual sourcing, allowing us to more readily maintain ground truth and ensure that every mutant violates some aspect of the property specification"; "We then measure if the strategy was able to solve the task, i.e. find the injected bug in all trials within the given time frame. Multiple trials account for the non-determinism of random generation strategies". Shi, Keleş, Goldstein, Pierce, Lampropoulos, "Etna: An Evaluation Platform for Property-Based Testing (Experience Report)", ICFP 2023. [KWIC] — [Exa copy](https://exa.ai/library/publication/spc8t18vds8)
- **Mutation analysis for fuzzers [summary; venues from memory, not confirmed]:** Görz, Mathis, Haßler, Güler, Holz, Zeller, et al., "Systematic Assessment of Fuzzers using Mutation Analysis", 2022 preprint (USENIX Security 2023) — [Exa copy](https://exa.ai/library/publication/6kgnvg14n6x). Vikram, Laybourn, Li, Nair, OBrien, et al., "Guiding Greybox Fuzzing with Mutation Testing" (Mu2), 2023 (ISSTA): corpus members are kept when they kill previously surviving mutants — [Exa copy](https://exa.ai/library/publication/3fzwy3yyvjp)
- **Seeded bugs to compare schedulers (see section 1):** P# FAST 2016, taPCT OOPSLA 2019, ModelFuzz OOPSLA 2025, TU Delft HotStuff and PBFT theses.
- **Grey literature, closest match to part (a) of the claim.** A repository describes itself as "Deterministic simulation testing: virtual clock, network and disk, seeded fault injection, linearizability checking - measured by how many seeds it takes to catch twelve planted Raft bugs". README: "Twelve defects, each one a mistake that has been made in a real Raft, planted one at a time. The number that matters is not the tick in the column - it is how many seeds it took"; the results table has columns "mutant | seed | caught by"; and "`kv_no_dedup` and `local_read` are caught only by the linearizability checker, and never by any Raft invariant." Control: "Seeds run against the unmutated implementation | 2,000", "Safety or linearizability violations | 0". `asp53826/dst-harness`, GitHub, created 2026-07-31, 0 stars, single author, Python. [README read via KWIC] — [GitHub](https://github.com/asp53826/dst-harness). Not peer-reviewed; results not reproduced by me; the mutants are hand-written, not operator-generated; no reached/differed classification of survivors is described.

### Inferences
- "Corpus member value measured by mutants killed" has a direct precedent in Mu2 (fuzzing corpus admission by mutation score), though for sequential Java and not for seeds of a simulator.
- The `dst-harness` repository shows that the per-oracle reading of part (a) (which invariant catches which planted defect, and at what seed cost) has been done at least once in public, two months before today's date. It is weak as prior art on provenance grounds, but it makes "nobody has graded DST oracles with planted defects" false as a blanket statement. The industrial-practice researcher should check whether larger projects do the same.
- I found no work that compares fault-injection policies or workload generators for a distributed system against an operator-generated mutant population.

### Gaps
- Bradbury 2007 was read only as an abstract; its numerical results for ConTest vs JPF are not recorded here.
- Whether FoundationDB, TigerBeetle or Antithesis use planted bugs or mutants internally is the other researcher's scope; query q25 surfaced only vendor overviews that Exa's summaries did not connect to mutation.
