**The resolver.** I prototyped your suggestion to check it holds before asking you to build it:

```sh
wd=$(realpath "$1") || exit 45
case "$2" in /*) p="$2" ;; *) p="$wd/$2" ;; esac
tail=""
while [ ! -e "$p" ] && [ ! -L "$p" ]; do
  tail="/${p##*/}$tail"; p="${p%/*}"; [ -n "$p" ] || p=/
done
base=$(realpath "$p" 2>/dev/null) || exit 44
target="${base%/}$tail"
case "$target" in "$wd"|"$wd"/*) ;; *) exit 43 ;; esac
```

Under both the GNU and the BSD-like `realpath` it gives the same verdict on 14 paths: existing and
new files, three missing levels deep, a name with a space, a symlink that stays inside, symlinks
out (existing target, new file, new nested file), and absolute paths inside and outside. For the
paths without a dangling link it agrees with `realpath -m`.

Things to carry into the PR:

- **Dangling symlinks.** The walk has to stop at a dangling link (`-L`), not walk past it; a write
  through one creates the file at the link's target. GNU `realpath -m` resolves it and refuses with
  43. BSD `realpath` can't resolve it, so the sketch refuses with 44. Refusing is right either way.
- **Fail closed in both guards.** With no GNU-only flag left, any failure of the resolver can refuse.
  That removes the "let through as before" branch in `validate_path_common` and the disagreement
  between the two guards.
- **Verifier.** The `has_realpath_m` probe and the SKIP in `verify_native_path_guard` go; the
  symlink checks are FAIL everywhere again. A dangling-link case would be worth adding.
- The native guard runs `bash -lc`, the extension `bash -c`. One shared script, one way to run it.
